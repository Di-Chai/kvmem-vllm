# KVMem + vLLM 大海捞针测试（2026-10-14）

本轮验证现有实现。正式矩阵为 qw3 原始 180 题，历史 KV 只保存在 CPU 内存，
不使用 SSD/NVMe，不启用重算。180/180 请求完成，零技术错误；长文准确率和
单请求延迟尚未达到旧 qw3 参考结果。流程验收通过不等于质量等价。

## 冻结样本和参数

来源为 `official_template_20260927/cohort.json`：四类任务
`niah_single_2`、`niah_multikey_2`、`niah_multivalue`、`niah_multiquery`，
每种长度包含深度 10/30/50/70/90% × seed 1000/2000/3000 × 四类任务，
64K、128K、256K 每档 60 题，共 180 题。

直接载入原始 little-endian int32 token ID 文件，逐文件校验原始 SHA256。
完整保留输入、公开 Query 和每条针的 token 坐标。实际输入长度分别为
65,493–65,495、131,029–131,031、262,101–262,103。
服务允许 524,288 的逻辑历史长度，GPU 上仍只保留 K+G 的密集位置，
原始 256K 输入无需为输出让位，不修改模型 RoPE 频率。

对齐原始 32K 协议：K=32,768、G=16,384、B=32、sink=1,312、recent=10,496、
普通 prefill 块上限 2,048、guided Query 上限 512、原生 MTP(k=4)。
输出上限 8,192，thinking 上限 4,096，达到上限时强制插入 qw3 原始过渡语和
`</think>`。temperature=1、top_p=.95、top_k=20、min_p=0、presence_penalty=0、
repetition_penalty=1，随机种子逐题沿用源样本。

当前模型为 NVFP4 权重、FP8 KV，保留编译和 CUDA Graph、原版 MeanK CUDA
评分、guided Query 和 Query relevance history。每题使用独立 session 和
cache salt，结束后释放历史，不跨题复用检查点。每题只有一次公开 Query，
因此本实验不用于证明历史评分跨轮积累的收益。

旧 qw3 结果使用 Q8 权重、FP8 KV，并曾开启 CacheBlend 重算；用户要求本次不重算。
因此本次与旧结果共享冻结题目及上述协议，不能将分数差异只归因于推理引擎。
原版采用独立 prefill-only 请求，本次在一个请求内先按时间顺序完成容量驱动
prefill，再在公开 Query 边界重选、装配和重放。不得把这两种执行协议说成完全相同。

## CPU 历史存储与并发

`archive_backend="cpu"` 选择不可变的纯 CPU 历史存储。它保留发布、读者租约、
命名空间隔离及回收协议，不创建 NVMe arena，不压缩或改变 BF16 raw-K / FP8-V。
`cpu_read_cache_bytes=100 GiB` 在此模式下限制 CPU 历史存储容量。
容量不足时不会自动落盘。机器没有启用 swap。

测试入口最多同时发出 8 个请求，并按每题完整历史、输出上限和 G 暂存量预留
内存额度。CPU 容量之外保留 8 GiB 余量；长输入等待额度释放，输入不被截断。
实测 64K/128K 最多 8 路，256K 最多 6 路同时准入。原生采样最多看到 4 路
历史同时达到约 256K，不能把 6 路请求并行当作 6 路完整长文稳态 decode。
该额度管理属于测试入口，不能据此宣称通用服务的 CPU 准入已经全部完成。
请求 HTTP 返回后，还需确认历史回收完成才归还额度。

样本、响应和诊断 JSON 可以写到磁盘；禁止落盘的是历史 KV。通过运行时
`archive_backend`、`disk_read_bytes`、`disk_write_bytes` 和 `nvme_capacity_bytes`
检查这一点，并保存实际并发与内存占用证据。

## 评分与证据审计

直接载入 qw3 冻结脚本中的 `score` 函数并记录文件哈希。只评分 `</think>` 之后的
最终答案，规范化千位逗号，计算完整数字覆盖率和整题数字集合全对率。
数字集合全对不自动证明多名称对应关系正确。覆盖率是逐题宏平均。
未闭合思考或未形成最终答案按失败计分，不使用思考中的数字补分。

另行检查每条针的完整证据区间是否被 Query 重选后的历史页覆盖。证据坐标和
标准答案仅用于离线审计，不发送给模型或用于选页。每题检查完整输入计数、
恰好一次 Query 重放、原版评分后端、K 上限和 Query history 提交。
技术错误和答案错误分别记录，不丢弃低分样本。

## 吞吐口径与当前调度限制

首批隔离的 8 路 64K 请求累计输入 523,946 tokens，最大原生 TTFT 为
97.879 秒，有效 prefill 约 5,353 输入 token/s。该数值包含历史维护、
选页、装配、guided Query 及首批预热，并非纯 GPU kernel 吞吐。
这些请求输出只有 101–331 tokens，不足以验收稳态合计 decode。
原始指标见 `full180/first8-performance.json`。

随后 128K 连续混合负载的一个约 60.25 秒窗口，已接受历史计数推算的
输入处理速度约 5,218 token/s，输出约 12.15 token/s。该输出速度包含
与其他请求 prefill、刷新竞争造成的停顿，不能替代纯 decode 基准。
方法及窗口在 `full180/live-mixed-throughput.json`；同步装配累计约
7.89 秒，guided Query 约 1.78 秒。刷新事件的起止时间按整个 batch
记录，多请求共享同一时间区间，不能简单累加为额外开销。

当前服务日志已确认 `enable_chunked_prefill=True`。普通 prefill 每请求
上限 2,048，但整个 batch 上限为 16,424，多个长请求仍可同批前进。
启动器在 request planning 模式下会把 batch 上限规范化为
`G + max_num_seqs * (draft_tokens + 1)`，以容纳完整 Query 原子重放；
直接在原始配置中调小 `max_num_batched_tokens` 会被覆盖。

改善混合负载需要将普通 prefill 的全 batch 计算预算与 Query 重放容量
分离，并验证 decode-only cadence；更进一步要让历史准备只暂停需要
刷新的请求。目前装配和 private guided forward 仍同步阻塞同 batch。
这些是待测调优方向，本轮冻结准确率矩阵不在运行中切换参数。

## 完整 180 题结果

| 输入长度 | 题数 | 当前数字覆盖率 | 当前数字集合全对 | 旧 qw3 覆盖率 / 集合全对 |
| --- | ---: | ---: | ---: | ---: |
| 64K | 60 | 100% | 60/60 | 100% / 60/60 |
| 128K | 60 | 92.50% | 45/60 | 99.58% / 59/60 |
| 256K | 60 | 65.42% | 30/60 | 97.92% / 58/60 |

单键查询的 `niah_single_2` 和 `niah_multikey_2` 三档均为 100%。多答案任务下降明显：
128K 的 multivalue / multiquery 覆盖率为 80% / 90%；256K 为 21.67% / 40%。
256K 两种多答案任务均没有一题数字集合全对。不得用单键题结果替代整体质量。

每档有 150 条针。最终页均包含全部 150 个答案数字；名称覆盖分别为 150/148/148，
完整证据句覆盖为 150/120/118。128K 漏答 18 个数字，名称和数字都已被选中；
256K 漏答 83 个，其中 81 个名称和数字均已被选中，另外 2 个只完整覆盖数字。
这只能排除相应数字完全未选入的情形，不能证明装配后的模型行为正确。

另有 `niah_multiquery_n131072_p90_s1000` 将 thinkable-literate 与 secretive-tower
的数字互换；原版数字集合指标仍通过。上述主表保留原版评分，显式名称绑定错误
另行报告。证据坐标与答案始终只用于离线审计。

180 题输入 SHA、完整输入计数、唯一 Query 重放、qw3 CUDA scorer、K 上限和
Query history 提交均通过；180 题终态历史长度均等于输入 + 输出 − 1，且已回收。
运行前冻结的 81 个源文件／配置在主矩阵中没有改变。

## 完整端到端延迟

| 输入长度 | 旧 qw3 单请求平均 | 当前 HTTP 处理平均 | 当前含 CPU 准入等待平均 | 当前平均 TTFT | 输出阶段平均耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 64K，8 路 | 25.58 秒 | 99.09 秒 | 99.11 秒 | 62.05 秒 | 36.38 秒 |
| 128K，8 路 | 46.94 秒 | 199.19 秒 | 199.20 秒 | 125.24 秒 | 73.18 秒 |
| 256K，6 路准入 | 89.86 秒 | 290.32 秒 | 381.70 秒 | 228.57 秒 | 60.92 秒 |

旧耗时为 `ingest_seconds + answer_seconds`，排除逐题进程启动和 reset；当前
处理耗时为 HTTP 请求执行至完成。所有口径均不计测试执行器尚未分派题目的队列。
180 题中没有任何一题比对应旧单请求的处理延迟更低。生成长度并不完全相同：
三档旧平均输出约 229/256/334 tokens，本版约 216/244/238 tokens。

256K 两题 CPU 准入等待分别为 2,713.90 和 2,767.93 秒，暴露了测试额度队列
非 FIFO 导致的饥饿；其余题的此项等待均低于 0.1 秒。均值必须包括这些慢请求。
这不是 GPU 生成这两题本身用了 46 分钟，也不是已经完成的生产公平性验收。

整批从首次准入到最后回收为 5,222.30 秒（87.04 分钟），累计输出 41,867 tokens。
旧 180 题请求耗时相加为 9,741.99 秒（162.37 分钟），本轮批量处理约快 1.87 倍。
旧值不是含逐题模型加载的实际 campaign wall time；当前包含首批 preflight 到
主测试的间隔。量化、重算和执行协议也有差异，不能视为纯引擎或纯并发加速比。

64K/128K/256K 分组从首次准入到最后回收分别为 843.40/1,625.40/3,027.92 秒，
包含相邻长度交叠，不应直接相加。整轮输出约 8.02 token/s，主要时间用于输入处理；
这个数字不能代替独立的稳态 decode 吞吐。

主矩阵共 511 次资源采样，历史 KV 磁盘读写与 NVMe 容量始终为零，没有 swap。
最低可用 RAM 约 9.58 GiB；最多同时接受约 150 万历史 tokens。
所有 CPU 历史和临时 buffer 的总内存仍需单独计量，100 GiB 不是进程总 RAM 上限。

`scripts/analyze_niah.py` 生成 `full180/offline-audit.json`，包含逐题配对、选页证据、
绑定错误和资源统计。源响应、原始输入、事件及最终原生快照均留在该目录。

## 独立固定输出吞吐

在 180 题结束、历史回收后，保持同一服务和配置，运行 8 个独立 session，
每路输入 50,006 tokens、固定输出 4,096 tokens。输入沿用此前 guided/history
基准文件；temperature=0、ignore_eos=true，使用 SSE token ID 和终态 usage 双重计数。

| 指标 | 结果 |
| --- | ---: |
| 8 路共同稳态 decode | **860.71 输出 token/s** |
| 同窗口原生接受历史速率 | 863.96 token/s，独立佐证 |
| 稳态窗口长度 | 36.47 秒 |
| 原生 8 路稳定窗口覆盖率 | 99.26%，无窗口内 prefill/刷新污染 |
| 包含全部准备的整轮输出吞吐 | **313.49 token/s** |
| 整轮耗时 / 输出总数 | 104.53 秒 / 32,768 tokens |
| TTFT p95 | 65.03 秒 |
| 有效输入处理速率 | **6,146 输入 token/s** |

有效输入速率按 400,048 输入 tokens / 最后一路首 token 到达的 65.09 秒计算，
包含 CPU 历史维护、选页、装配和 guided Query；不是纯 prefill kernel 吞吐。
与 NIAH 的 8.02 token/s 整轮输出不可直接对比：NIAH 输入更长且只生成短答案，
还有不断到来的其他长 prefill。

8 路都实际执行 Query 重放、选页和历史评分，终态历史均为 54,101 tokens。
private guided 长度分别为 42、1、1、1、1、1、1、1；这证明路径执行，不证明
每个内部 Query 都有充分语义。其停止／回退差异仍需处理，不能用此性能结果
宣称 guided 语义已经与 qw3 完全等价。

此前相同输入的 729.37 token/s 基准使用 MTP3、B128、guided 上限32、CPU cache
和 NVMe，以及不同检查点／验收设置；本次为 MTP4、B32、guided512、纯 CPU、无保留
检查点。因此 860.71 与 729.37 的差值不构成某一项优化的控制实验结论。
原始数据：`artifacts/niah-20261014/decode50k-c8-cpu/results.json`。

## 同版本单请求诊断

| 样本（seed=1000） | 单路耗时 | 主矩阵并发耗时 | 单路 / 并发覆盖率 |

| 64K single，深度10% | 11.85 秒 | 100.65 秒 | 100% / 100% |

multivalue 两次漏答的数字不同，采样和输出长度也不同；三个样本不能替代完整单路

## 本轮发现的边界

- 测试入口的 CPU credit gate 使用条件变量竞争额度，没有 FIFO 保证。
  256K 的两题被后续题目反复抢先准入；最终统计必须包括其等待时间。
  这属于测试入口，不能拿当前结果证明生产服务具有公平排队或 SLO 保证。
- private guided Query 的停止／回退语义还未完全对齐当前 qw3：本版遇到换行即停止，
  会捕获前导空白；qw3 跳过前导空白，并校验结构化／未终止输出。私有生成也未使用
  qw3 的 MTP 加速。这些差异的质量影响需单独量化；主矩阵未中途修改它们。
- 新纯 CPU archive 的整条记录读取仍通过 Python 内存复制；区域 gather 使用原生
  单任务路径。`cpu_gather_workers` 目前只接入 `CachedArchive`，没有接入新
  `MemoryArchive`。其独立开销尚未做控制实验，不能把全部 host prepare 时间归于此。
- 本矩阵是独立冷会话，每题一次 Query；它不验证纯 CPU 后端的跨轮恢复收益。
  原生入口的并发 session 也不替代带鉴权的多租户网关验收。
