# 16 路真实文档混合请求：增长、卸载与短请求完成

2026-11-06。在[第二阶段实现](dynamic-memory-phase2-20261106.md)上补充有限真实输入实验。运行时源码与第二阶段最终冻结版本完全相同；此次新增客户端和分析，没有修改 K/G、选块规则、刷新时机或调度算法。

结论：16 个 HTTP 请求能够由当前动态模式共同处理，GPU 页面不足时确实发生暂停及 SSD 恢复；但驻留数不会按预设的 16→8→4 档位切换。短请求可以先完成，也可能因准入排队很晚才执行。测试区分了“自然完成减少请求数”与“仍未完成的请求被换出”。

## 当前卸载规则

- 每次调度先检查下一次完整计算操作所需的物理页，不足则暂缓该操作并在安全边界选择换出对象，不等待 CUDA OOM。
- 快照完成并确认后才归还 GPU 页；CPU 暂存紧张时将暂停快照写到 SSD；恢复取得实际页面和 CPU 暂存后继续原请求。
- 尽量避开接近结束的 decode，保留恢复后的驻留时间和公平轮换规则。接近结束按 `max_tokens - num_output_tokens` 判断，无法预知自然 EOS。
- `max_num_seqs` 是原生执行槽上限。暂停请求保留其槽；改变的是 GPU 页所有权，并不把该设置实时改成 8 或 4。
- 压力来自配置的共享 KV 页池，不是整卡显存剩余量探测；GPU 总页池仍在启动时建立。

## 实际数据与配置

数据来自官方 [LongBench 数据仓库](https://huggingface.co/datasets/zai-org/LongBench/tree/main)的 `5e628be` 版本，使用[官方任务模板](https://github.com/THUDM/LongBench/blob/main/LongBench/config/dataset2prompt.json)和[输出上限](https://github.com/THUDM/LongBench/blob/main/LongBench/config/dataset2maxlen.json)。按输入长度区间与原文件顺序各取四条，不按答案或运行速度挑选。

| 数据 | 数量 | 实际完整输入 tokens | 输出上限 |
| --- | ---: | --- | ---: |
| Qasper：论文问答 | 4 | 3,440 / 3,080 / 3,550 / 3,300 | 128 |
| HotpotQA：多文档问答 | 4 | 2,332 / 3,385 / 3,642 / 1,931 | 32 |
| GovReport：报告摘要 | 4 | 11,054 / 9,785 / 8,769 / 8,131 | 512 |
| MultiNews：新闻摘要 | 4 | 6,525 / 6,088 / 5,646 / 5,219 | 512 |

总输入 85,877 tokens，文档没有裁剪、拼接填充或复制到指定长度。使用本地 tokenizer 的 user chat template，关闭 thinking，temperature=0、seed=104729；允许自然 EOS。达到输出上限的响应单列为截断，不算自然完成。

硬件和模型沿用 RTX PRO 6000、Qwen3.8-27B NVFP4、FP8 KV、native MTP 1、eager。K/G 均为 2,048，prefill chunk 128，最大上下文 16,384；为发送 16 路，将 `max_num_seqs` 设为 16、批次 token 上限设为 2,048。历史 CPU 768 MiB、历史 SSD 8 GiB；暂停快照 CPU 512 MiB、SSD 8 GiB。HTTP 请求通过屏障同时发出，两次性能观察的启动时间跨度分别为 7.34 和 6.54 ms。

这些是不同页池大小下的一次有限负载观察，不是旧算法/新算法 ABBA。每臂只有单请求预热，部分多请求形状仍可能首次编译；不作为稳态 SLO 或最大吞吐结果。文件接口 I/O 使用 OS page cache，不是裸 SSD 带宽。

## 为什么不能假设 16 个一定会因增长降至 8 个

本模型实际原生页几何为：三个 Mamba/GDN 状态组，每组每请求固定 2 页，共 **6 页循环状态**；attention 页的 block size 为 **1,584 tokens**。因此运行请求起步至少需要 **7 页**，完整 K+G 窗口上界约 **9 页**。

16 个请求起步需要至少 112 个可用页；16 个满窗口请求上界是 144 页。本次宽裕池有 122 个可用页，增长时少量换出即可推进。不能把这个配置的 G 增长解释为每请求占用翻倍，也不能承诺固定降至 8 或 4。其他模型和 K/G 配置需要按其真实页几何重新计算。

## 两组真实并发结果

| 指标 | 紧张池 `tight-r2` | 宽裕池 `wide` |
| --- | ---: | ---: |
| GPU KV backing 配置（十进制 GB） | 2.5 | 6.8 |
| 可用原生页（另有 1 个 null page） | 44 | 122 |
| HTTP 并发峰值 / 完成请求数 | 16 / 16 | 16 / 16 |
| 同时持有 GPU 页的请求峰值 | 6 | 16 |
| 实际 public forward 批次请求数峰值 | 5 | 15 |
| 暂停 / 恢复次数 | 6 / 6 | 2 / 2 |
| 暂停快照 SSD 写入 / 读回 | 各 2,465,759,256 bytes | 各 475,299,844 bytes |
| 自然 EOS / 达到输出上限 | 9 / 7 | 8 / 8 |
| 从提交至全部 HTTP 完成 | 112.72 s | 64.92 s |
| 实际输出 tokens | 4,108 | 4,152 |
| 观察到的输出 tokens/s | 36.44 | 63.96 |

这组对照同时改变了可用 GPU 容量、排队与批次组合，而且自然输出数量不同，不能解释成单一卸载优化带来的加速。单次 public forward 的峰值也不等于同时驻留峰值：部分驻留请求可能处于维护或等待步骤。

宽裕池的时间线如下，时间以最早 HTTP 请求启动为零点，是服务端已发布状态的采样：

| 时间 | 尚未完成 HTTP 的请求 | GPU 驻留 | 已暂停 | 解释 |
| ---: | ---: | ---: | ---: | --- |
| 0.43 s | 16 | 16 | 0 | 16 个请求已经同时持页 |
| 5.71 s | 16 | 15 | 1 | 尚无请求完成，因增长真实换出一个请求 |
| 6.27 s | 15 | 14 | 1 | 首个短请求完成并回收 |
| 7.62 s | 15 | 15 | 0 | 被暂停请求取得页面并恢复 |
| 10.66 s | 12 | 11 | 1 | 第二次增长触发暂停 |
| 11.55 s | 12 | 12 | 0 | 再次恢复 |
| 17.03 s | 8 | 8 | 0 | 八个短问答已全部完成；没有八个暂停请求 |

宽裕池两次捕获均由 `resident_growth` 触发，发生于 prefill 的 history 1,536 和 3,200。此次没有覆盖长 decode 逐步填满整个 G 的场景。紧张池的六次捕获则分别来自增长 1 次、公平恢复 4 次、等待请求公平推进 1 次，并非全部都是显存增长直接触发。

短请求方面，宽裕池的八条问答均在 6.08–16.84 s 完成。紧张池中六条在 4.87–18.72 s 完成，但两条仅输出 4 和 3 tokens 的 Qasper 请求分别等到 76.55 s 和 83.61 s；它们自身没有被换出，延迟来自准入和调度等待。当前实现并不提供最短作业优先或短请求延迟保证。

## 恢复正确性与输出差异

额外的 `tight-verified` 使用同一 16 条完整输入、2.5 GB 页池，并启用真实 GPU 恢复字节核验。16 条请求全部完成，发生 **10 次恢复，全部来自 SSD，10/10 成功**；每次覆盖同一模型的 **131 个字段**，合计核验 **4,036,067,368 bytes**。回执身份唯一、与恢复轨迹逐次匹配，字段集合与第二阶段核验一致，没有缺失或失败。该轮包含额外读回和同步，不参与上述性能对比；暂停次数也受实际到达与执行时序影响。

三轮最终都满足：请求数和 GPU 页占用归零，可用页完全归还；历史 CPU、历史 SSD extent/file、快照 CPU/SSD、承诺额度及在途 I/O 全部回收。测试结束后没有遗留 GPU 模型进程。

**严格输出等价没有通过。** 紧张池与宽裕池的 16 对输出中，7 对 token IDs 和文本完全相同；1 条短问答仅有大小写区别，8 条摘要的生成内容不同。紧张池有 7 条、宽裕池有 8 条摘要达到 512-token 上限，不能把截断算作完整摘要质量通过。当前没有对这些样本进行完整 LongBench 质量评分，也没有单独隔离数值差异的原因。GPU 字节恢复通过不能替代端到端输出等价或任务质量验证。

汇总状态明确记录为 `lifecycle_and_byte_checks_passed_output_equivalence_not_established`，不会把输出差异归入“全部通过”。新客户端及相关回归共 39 项测试通过，覆盖自然 EOS、截断与 token 计数、以及完成导致的驻留下降和压力导致的下降之间的区分。

## 证据与复现

根目录 `artifacts/dynamic-memory-mixed16-20261106/` 保存：

- `data/sources.json`：官方下载地址、字节数与 SHA-256；`fixture.json`：固定的原始样本身份、完整输入 IDs 和参考答案。
- `runtime/`、`source.json`：同一份冻结运行时；`environment.json`：依赖版本与 tokenizer 文件摘要。
- `tight-r2/`、`wide/`、`tight-verified/`：每条请求、SSE token burst 时间、资源快照、恢复轨迹、完整输出及最终回收结果。
- `analysis.json`：由 `analyze-results.py` 重建的生命周期、并发、字节核验和严格输出差异汇总。
- `tight/interruption.json`：首个启动在正式请求发送前因对话中断而停止，未计入任何测量。

已有冻结输入可用于新的独立实验目录或新的 arm 名称；脚本拒绝覆盖原 arm：

```bash
PYTHONPATH=src:scripts python scripts/benchmark_dynamic_mixed.py \
  --root artifacts/dynamic-memory-mixed16-20261106 \
  --arm new-tight --gpu-bytes 2500000000
```

添加 `--verify` 可启用逐次恢复字节核验。保持当前已验证的 eager / 同步组合；不要把这些有限观察扩展为数小时持续负载、突发补位或任意并发量的稳定性结论。

后续数据可选 [LMSYS-Chat-1M](https://huggingface.co/datasets/lmsys/lmsys-chat-1m) 的真实聊天长度分布，以及本地 DeepSWE / Terminal-Bench 的请求与工具等待轨迹。聊天回放适合检查长短交错和到达突发；Agent 轨迹适合检查暂停、工具等待和会话再次唤醒。正式工具执行与任务评分应单独进行，不能以冻结请求回放代替。
