# 连续调度中的 prefill 成本合并

日期：2026-10-16。实验功能默认关闭，相关 CPU 回归 406 项通过，报告为
`artifacts/prefill-coalescing-cpu-20261016-r1.xml`。冻结实验
`artifacts/timed-prefill-coalescing-20261016-r1` 已通过真实模型验收并完成一对性能
初测：整窗有效输出 138.03 → 149.00 token/s（+7.95%），实际完成的 prefill
没有减少。尚未达到三对均改善且中位至少 10% 的稳定增益门槛，默认继续关闭。
两个性能版本只切换合并开关，均逐步计时，不与旧版间隔采样的数值直接比较或相加。

热恢复原始 gate 已通过 8/8 次，且目标会话实际执行五个 4096-token 普通
prefill，每个均同批调度三路 decode。其后 M 检查点恢复验证 history=69631
（65536 输入 + 4096 输出 - 1），包含 17 个 attention 层（含 1 MTP）和 96 个
recurrent 张量，逐字节一致。压力回收后的原始 gate 也通过 8/8 次；两个原 gate
及实际合并执行门槛合计报告为实验目录 `correctness-gate.json`。这些正确性证据不
代表合并已带来性能收益。校准中已出现无收益和样本不稳时回到 2K 的行为。

## 第一对性能结果

四个逻辑用户、同一 16 轮来源轨迹，NVFP4/FP8 KV/MTP(k=4)、K/G 各 128K、
100 GB CPU 历史，原生槽仍为四个。两轮固定工作预热之后，各测完整 300 秒。

| 指标 | 2K 连续基线 A0 | 成本合并 P1 |
| --- | ---: | ---: |
| 窗口内 accepted 输出 | 41,410 | 44,701 |
| 整窗有效输出 token/s | 138.03 | 149.00 |
| public prefill 完成位置数 | 552,120 | 552,926～554,714 |
| public prefill 完成 token/s | 1,840.40 | 1,843.09～1,849.05 |
| GPU 时间加权利用率 | 83.63% | 82.67% |
| 窗口内完成的请求 | 65 | 69 |
| 输出事件间隔 p99 | 0.772 s | 0.996 s |
| 窗口后收尾（不计吞吐） | 26.26 s | 42.30 s |

有效输出增加 3291 token（7.947%）；候选在窗口内至少多完成 806 个 public
prefill 位置，未重复上次 phase 策略少做约 17%～19% 输入的情况。不过候选在
T1 有一条尚未输出首 token 的请求，后续收尾还生成 8264 token，基线为 3810。
收尾变长包含更多在途生成工作，不能直接等同于 prefill 欠账或忽略它的延迟。
候选发出的新输入为 554641 token，基线 552051；窗口边界进度并不完全一致。

窗口内实际执行 47 个 4K 普通 prefill 模型步：23 个校准、24 个测得成本改善后
批准的批次，46 次与三路 decode 同批、一次与两路同批。基线没有 4K 普通
prefill。完整混合步从 330 降至 268 个，模型总成本约 151.89 → 148.98 秒，
单步中位数约 437 → 495 ms；同上下文桶四路纯 decode 中位数约
44.519 → 44.586 ms，基本不变。这是减少部分批次固定开销的调度实验，不是
decode 内核提速证明，整窗增量仍有工作位置和运行波动的影响。

输出事件间隔最大值约 2.262 → 2.742 秒；全局超过 1 秒无 workload 输出的
间隔从 6 段、累计 9.24 秒增至 39 段、累计 49.61 秒。MTP 一个事件可能含多个
token，事件间隔不是单 token 延迟；全局无输出也不代表 GPU 空闲。p95 改善
不能覆盖 p99 和最长停顿变差的事实，不将本结果作为 SLO 或平滑性改善结论。

原生与客户端全运行（包括预热、正常清理与收尾）accepted 总量分别为
56451/64196，各自完全一致。两组 GPU 样本均覆盖完整 300 秒，零原生抢占、
零 KV 磁盘读写，最终请求/refresh/connector/owned blocks 均归零，GPU 进程已退出。

计数观察器有一个明确限制：两组退出前最后一次清理后的公共完成 fence 尚未
再次刷新到最终 JSON，A0/P1 分别保留 1 批、3/4 个 cleanup 输入位置未确认。
原始 `all_submitted_completed=false` 保留；没有将它改成 true。正式窗口的
prefill 完成边界已经闭合，原生全量输出核对和资源退休通过；这不能被写成
“全引擎所有观察器 fence 已完成”，也不计入窗口输入欠账。

本次只是一对持续供给初测，不是完整 DeepSWE 任务质量、真实工具执行或 SLO
验收，也未覆盖 active 容量耗尽后的全部重选压力。更大分块可能增加长尾；
吞吐增量不能单独证明延迟改善或全局最优。证据位于实验目录的 `comparison.json`、
两组 `saturated/results.json`、`diagnostic-comparison.json`、`correctness-gate.json`、
`cleanup-audit.json`。

上一版按阶段调度在约 113 秒 PREFILL 决策停留中，约 112.85 秒仍有 decode
已就绪；该统计不是 CUDA 执行时间。消除公开混批只取得 3.73% 的整窗输出增量，
同时少完成 17%～19% prefill、收尾更长。因此本轮回到连续 batch，不暂停已经
就绪的 decode，不将阶段切换或新增 CPU 就绪池混进优化。

已有日志中同组成、同上下文桶的 3 decode + 1 prefill 样本表明，部分混批固定
模型成本约 135 ms，而纯 decode 约 40 ms。50 ms 目标无法覆盖这部分固定项；
继续缩小块会重复支付固定成本。原日志不足以证明所有组成的最优分块，本次采用
有界、可退回的在线比较，不把一组拟合外推到全部请求。

## 策略

- `offline_prefill_coalescing=false` 为默认值；要求现有 `offline_agent_policy`，
  与 P/D phase gate、独立 adaptive/shared-cap 控制器互斥。
- 原普通输入分块保持 2048 token，候选上限 `offline_prefill_max_tokens=4096`。
  只对一个普通 prefill 参与者且剩余输入足够长的批次比较；未知组成和短输入沿用
  原值。不等待新输入凑块，也不通过零 token 额度推迟 prefill。
- 成本键包含 decode/prefill 人数及双方 active-context 桶。先有三个接近满 2K
  的观测，再发放最多三个 4K 校准授权。候选实际未提交可以退还；已经执行了超过
  基线的输入，即使最后被裁短或组成变化，也消耗校准额度，不能无限重试。
- 比较公开 prefill token 的 `model_ms/token` 中位数。模型段包含同批 decode、
  MTP、采样和相关捕获，不含前段维护；不能据单位输入成本改善宣称 decode 变快。
  至少三个满 4K 观测确认单位成本降低 5%、单步中位成本不超过基线两倍后才继续
  合并；样本不稳或无收益回到 2K。两倍是观测选择条件，不是硬 CUDA 时限或 SLO。
- 反馈新鲜度为 5 秒；模型 bank 保留 60 秒，最多 64 个键，每键 32 点。过期、
  缺失和不匹配反馈不能变成“零成本”。校准及回退原因需要记录。

## 语义与边界

KVMem MeanK、Action/Prefill attention、Query history、guided refresh、必留内容和
检查点语义不变。完整 Query replay 不进入普通合并学习，不拆原子 Query；原生
MTP 的 `1+k` 占位尾部保留，预算按实际公开输入而非占位 token 计算。

调度器仍沿用已有按请求异步恢复、CPU/GPU 准入和压力驻留。恢复未完成只跳过
自身。没有新增抢占、历史丢弃、SSD 缓存或容量重算。authority 数量仍受原生
`max_num_seqs` 约束，没有新增额外 ready 池。更大的混批可能增加输出长尾，
不能宣称吞吐和延迟同时改善。

## 验收

先做 CPU 策略、授权生命周期、分类、Query/MTP/native 边界及旧功能回归。随后
分别执行长等待热恢复和同步压力回收逐字节验收。热恢复负载让三路 32K 输入先
进入长 decode，再提交一路 64K 输入，必须记录实际大于基线的公开 prefill，
并在后续跨轮恢复中验证 KV、recurrent 和 MTP 状态。没有实际执行合并不能将
“开关开启”当作合并功能验收通过。

性能采用相同四用户 16 轮来源轨迹、相同预算、同两轮预热及各 300 秒窗口。
两组同一新 runtime、同一驻留策略、同一每步计时，仅合并开关不同。检查整窗
accepted 输出、实际 prefill 完成上下界、p99/最长输出间隔、GPU 利用率、末尾
输入欠账及收尾。仍使用完整 `[T0,T1)` 分母，部分输出照计，收尾排除；不以
较少完成 prefill 来证明总体效率提升。单对为初测，稳定收益需另做重复确认。

候选配置：`examples/qwen-nvfp4-coalesced-offline-agent-k128-g128.json`。
性能入口：`scripts/benchmark_coalesced_agents.py`。

## 八并发对照，2026-10-16

实验 `artifacts/timed-prefill-coalescing-c8-20261016-r3` 已完成一对各 300 秒的饱和
窗口。使用同一来源按清单顺序的前八个独立任务、每任务 16 轮冻结外部消息；前四个
任务的计划与此前四并发样本完全一致。新增四个任务保留自己的输入和输出配额，
没有复制前四个用户。仍采用两轮固定工作预热，窗口外正常排空。

原生 `max_num_seqs` 和客户端并发均为八；准备入口增加显式的 4/8 并发支持，
并拒绝客户端并发与原生槽不匹配。准备、冻结和实际启动参数相关回归 19 项通过。
runtime 源文件与已验收的四并发版本逐文件哈希一致，两组唯一差异仍为合并开关。

为容纳真实八路，这两组共同使用逻辑历史上限 512K、显存预算 0.81，关闭可选的
GPU raw-K 加速缓存，保留 resident V 复用。NVFP4、FP8 KV、原生 MTP(k=4)、
K/G 各 128K、100 GB CPU 历史及推进余量保持不变。实际 GPU 池为 914 页，
样本最坏预计需 892 页；完整 16 轮历史最长 174352 token，预计 CPU 历史及
推进预算上界约 83.08 GB。这是轨迹配额下的八并发测试，未验证八路同时生成满
128K，也不能与旧四并发的绝对吞吐直接作并发扩展归因。

| 指标 | 八路 2K 基线 A0 | 八路成本合并 P1 |
| --- | ---: | ---: |
| 窗口内 accepted 输出 | 67860 | 71201 |
| 整窗输出 token/s | 226.20 | 237.34 |
| public prefill 完成 token/s | 997.55～1018.03 | 1075.55～1079.57 |
| GPU 时间加权利用率 | 72.25% | 74.30% |

| 窗口内完成请求 | 79 | 83 |

整窗输出差额为 3341 token（4.923%），候选至少多完成 17258 个 public prefill
位置。然而首次普通大于 2K 的模型步到 T0+168.536 秒才出现；在此前相同长度的
区间内，A0/P1 已分别输出 46688/49883 token。3195 token、即整窗差额的
95.6%，出现在合并实际执行之前。候选也已在 T0+162.972 秒开始一个新的长文
epoch，基线在此边界前尚未开始。后半段两组输出为 21172/21318，但工作进度
已经不同。因此本次正差异不能认定为合并策略带来的提速。

P1 实际执行 32 个普通 4096-token 模型步，全部与七路 decode 同批，其中
14 次为校准、18 次为批准执行。纯八路 decode 模型步 A0/P1 分别有
1685/1734 个，中位约 69.984/68.941 ms；八个客户端请求同时在途的时间为
298.478/298.630 秒。模型步耗时和 SSE 事件间隔均不是单 token 延迟。

两组窗口内各有三次冷恢复、上传相同的约 20.97 GB 历史 KV，其余 82/86 次
为完整热恢复。冷恢复位于首次合并之前，中位耗时 11.969/10.261 秒；这部分
差异也是早期输出进度不同的因素，不能归因于合并。旧四并发窗口全部为热恢复，
没有这些 KV 上传。这里的上传量按窗口内开始的恢复任务汇总，不是精确的窗口
PCIe 带宽。

两组 GPU 采样覆盖率均为 100%；八个用户均有输出，零原生抢占、零 CPU 容量
等待、零 KV 磁盘读写。包括预热、清理与收尾的原生/客户端 accepted 总量分别
为 86183/94226，各自精确一致。最终请求、refresh、connector、owned blocks
及 reservations 全部清空，最后观察器完成 fence 均确认，模型进程已退出。
本轮没有额外声称完成新的八并发逐字节恢复或任务质量验收。

预备尝试全部保留：r1 在等待 GPU 空闲阶段取消，没有启动模型；原 1M 历史上限
和 0.72 显存预算的准入不足以保证八路。r2 在预热后的冷恢复中因可选 raw-K
缓存的延迟显存分配失败退出，不能作为性能结果；r3 的共同容量调整避免了该
失败。关闭非权威 GPU 缓存不丢弃 CPU 历史、不使用 SSD，也不引入容量重算。

结论仍为单对初测，吞吐改善未被证明可重复或可归因，输出长尾和排空时间变差，
未达到三对均改善且中位至少 10% 的门槛，默认继续关闭。原始证据见实验目录的
`comparison.json`、`independent-review.json`、`review.json`、
`preflight-audit.json`、`actual-capacity-check.json` 和 `cleanup-audit.json`。
