# 原生 vLLM：已有 32K KV 后持续 prefill 到 64K

2026-10-22 按用户要求完成单请求原生测试。不是两次独立请求的时间相减：
一个请求提交 65,536 个输入 token，连续建立 KV，在 32K、48K、64K 物理
边界记录已完成 CUDA event，并核验完整上下文、分块和事件链接。

原始记录：[native-growth32to64-20261022-r1](../artifacts/native-growth32to64-20261022-r1)。
结果：[growth-results.json](../artifacts/native-growth32to64-20261022-r1/growth-results.json)。

## 配置与计时

- 同机 RTX PRO 6000 Blackwell 96GB，单请求串行；Qwen3.8-27B NVFP4、FP8 KV、
  原生 MTP(k=4)、编译和 CUDA Graph 保留，batch=16,424，max-num-seqs=8。
- 原生模型内核未修改，不加载 KVMem connector、统计或归档。诊断 scheduler
  只限制分块边界，worker 记录非阻塞事件，正式计算前已撤去编译审计包装。
- 最大物理 prefill 块 14,336 token，实际块表为
  `[2048,14336,14336,2048,14336,2048,14336,2048]`。累计边界包括 32K、48K、64K。
- 输入为既有冻结长输入的前 65,536 token；SHA256
  `dc01e683aebcc373db4102256173a0bf7535db70c19b1d2d8c9c3f8a44cec015`。
  这是吞吐诊断，截取内容不包含原题末尾问题，不作准确性评分。
- 完整 64K 预热一次，然后三次有计时、三次关闭计时交错运行；两者都保留
  很小的请求识别/分块包装。prefix caching 关闭，各请求均重新计算完整输入。
- 每个阶段从本阶段首个模型开始事件到末个完成事件，包含阶段内空隙；
  不含阶段开始前的维护间隙。32K 边界前后间隙均值仅 0.358 ms，若以
  “前 32K 的结束事件”作为追加起点，32K→64K 为 5.302874 s，四舍五入仍为 5.30 s。
  最终 64K 块包含原生终止 prefill 的采样/MTP 路径。HTTP 首 token 时间另列。

| 32K→48K | 16,384 | 2.385636 s | 6,867.77 token/s |

32K→64K 三次分别为 **5.290846、5.308365、5.308335 s**。

子阶段均排除自身开始前的间隙，因此表中父区间与子区间相加存在亚毫秒差值。

## 核验与含义

42 项相关 CPU 测试通过。实模核验正式请求 token 数、物理块表、owner、
active/logical 长度和终止边界均一致，事件没有缺行。冻结脚本/输入通过 SHA
核验；FlashInfer 实际加载的 136 项配置与种子完全相同，Inductor 的 15 个
目标/MTP 共同内核通过实际启动执行审计，正式分发不保留该审计包装。
全部请求完成，清理记录及再次检查均显示 GPU 无计算进程；没有启动 DSH。

本测试支持：原生 vLLM 从空上下文建立 32K 的约 10.3K token/s，不能直接
作为已有 32K 上下文后追加输入的速度。随着 active KV 增长，原生后续阶段
也变慢。这里确实只有原生 active KV 参与 attention。

本轮 32K→64K 的上下文增长范围比 KVMem K32/G16 的稳定 32K→约48K 周期
更长，**不能拿 6,179.71 与 KVMem 完整256K的5,874.80直接计算净附加成本**。
32K→48K 的 6,867.77 更接近该周期，但新块表与既有 KVMem 的
`32+14336+1952` 不完全相同，仍需使用逐块匹配的对照进行严格归因。

准备期间复用了原有冻结工具，生成的 KVMem provenance 目录及旧形状用例
未执行。本次实际仅运行 `native/suite.json` 中的 8 个原生请求。
