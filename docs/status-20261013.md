当前版本 `0.1.0.dev1` 已完成**单卡、单原生服务的多用户试运行版本**：
认证、用户隔离、有限排队、公平准入和断流回收已接入公开启动入口，
并完成真实模型的最多 32 用户短请求测试。**生产任务质量、长期稳定性和
高并发长上下文吞吐尚未验收。** 本页更新覆盖
[2026-09-29 状态](status-20260929.md)中相应的待测项，其他限制仍然适用。

本文的实际模型测量来自本地 `artifacts/multi-user-20261013/`，不是模拟 HTTP
服务的单元测试计时。除另行注明外，下文产物路径均相对于该目录；大体积原始
产物留在本地供复核。

## 本次配置

- 单张 RTX PRO 6000 Blackwell；Qwen3.8-27B GGUF **Q8_0** 目标模型、
  **FP8 e4m3** 目标 KV、DFlash2 BF16 草稿，vLLM 0.30.0 V2 runner。
- 单 API 进程、TP=1、eager、同步调度、纯文本；原生 prefix caching 关闭。
- `max_num_seqs=8`、`max_num_batched_tokens=4224`、长 prefill 分块阈值 1024、
  `gpu_memory_utilization=0.72`、逻辑上下文上限 262144。
- KVMem 保持 **K131072/G65536/B128**；prefill cadence 8，异步归档回收，
  packed assembly 和 direct pinned reads 开启。
- 准入上限：全局 **8**、每用户 **2**、最多 **64** 个排队请求、排队超时 **120 秒**。
  **32 个客户端包含排队者，不表示 32 条生成同时在 GPU 上执行。**
- 会话 checkpoint 最多 **4 个**，总 payload 上限 **1 GiB**。
  32 个身份能提交请求，不代表能同时常驻 32 个长会话 checkpoint。
- 原生 Q8 与可选 Q8 Tensor Core 使用相同模型精度、请求与显式启动参数；
  两份 profile 仅 `q8_tensorcore` 不同。自动分配的 KV 页池不同：
  原生 1138 blocks、Tensor Core 1076 blocks，均保留 1 个空块。

默认和示例 profile 的 **`q8_tensorcore=false`**。本次最后启动的测试服务使用
Tensor Core 候选 profile；这不改变默认值，也不表示该选项已经通过任务质量验收。
配置证据：`multi-profile.json`、`multi-profile-tensorcore.json`、
`multi-server/launch.json`、`multi-server-tensorcore/launch.json`。

## 新增的多用户服务能力

认证与准入直接运行在原生 vLLM 服务的 ASGI middleware 中。每个用户使用独立
Bearer API key；服务端从已认证身份生成 cache namespace，并重写内部请求 ID。
用户可重复使用可见 session ID，但不能自行指定另一用户的内部隔离范围。

准入在整个流式响应和取消清理期间持有配额。达到单用户上限时，其他仍有配额的
用户可以继续进入；队列满或等待超时返回带 `Retry-After` 的 HTTP 429。
活跃断连会取消原生生成，排队断连会移除等待项。会话池满时仍保留同会话串行，
诊断历史限制为最近 256 条完成记录。

公开入口提供认证后的 `/v1/models`、`/v1/chat/completions`、`/v1/completions`，
`/health` 保持可用；管理端点不暴露。认证 smoke 实测无 key 返回 401、有效 key
访问模型返回 200、私有 metrics 返回 404。公开 profile 启动、首请求自动 arming
和实际生成也已通过，覆盖旧状态中的该项待测。

证据：`authentication-smoke.json`、`native-startup-smoke.json`。
配置方法见 [multi-user-serving.md](multi-user-serving.md)。

## 同一请求条件下的吞吐与首字延迟

两条路径都使用 `/v1/chat/completions`、关闭 thinking、256 个 filler words，
实际输入均为 **290 token**，强制生成 **128 token**。每个并发客户端顺序提交
2 次请求；依次测试 1、4、8、16、32 个不同用户，各路径合计 **122/122 成功**，
没有拒绝或失败。以下是每档完整测试窗口的输出 token 总量除以 wall time，
包含排队、prefill、客户端启动和最后一个响应完成；不是纯 decode 峰值。

| 客户端／用户数 | 请求数 | 原生 Q8 tok/s | Tensor Core tok/s | 吞吐比 | 原生 TTFT p50 / p95（秒） | Tensor Core TTFT p50 / p95（秒） |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 2 | 34.80 | 42.05 | 1.21× | 0.98 / 0.98 | 0.33 / 0.33 |
| 4 | 8 | 47.23 | 92.86 | 1.97× | 4.25 / 4.26 | 1.68 / 1.68 |
| 8 | 16 | 49.42 | 130.38 | 2.64× | 5.66 / 9.01 | 3.21 / 3.22 |
| 16 | 32 | 49.25 | 131.61 | 2.67× | 27.92 / 28.88 | 9.72 / 11.08 |
| 32 | 64 | 49.65 | 130.15 | 2.62× | 69.50 / 69.55 | 26.80 / 26.85 |

32 用户档的完整请求延迟 p95 为原生 **82.55 秒**、Tensor Core **31.49 秒**。
请求能够排队完成，但超过 8 个客户端之后吞吐基本持平，等待时间明显增加。
这支持容量与排队行为的结论，不能写成“32 用户低延迟实时服务”。

该对照保持请求和显式服务配置一致，但自动 KV 页池容量不同，且每档只有 2 轮。
这是一次顺序执行的短请求 sweep，没有重复实验置信区间，也没有匹配输出质量。
首字延迟按首个非空可见内容 SSE chunk 计算；chunk 不等于 token，token 数来自
服务端 usage。闭环请求到达速率不能当成服务吞吐。

证据：`load-native/results.json`、`load-tensorcore/results.json`。
测量方法和复测命令见 [multi-user-testing.md](multi-user-testing.md)。

## 隔离、过载、公平性与取消恢复

原生和 Tensor Core 均通过 1/4/8 并发的合成唯一标记检索，以及两波各 **32 用户**
同时使用相同可见 session ID、request ID、caller cache salt 的碰撞探测。
每波 32 个输出均精确匹配本用户标记，未检测到其他用户标记；断开长生成后的
同会话短请求也完成。它证明这些合成输入的输出隔离，不能单独证明所有缓存路径
和长期复杂任务的隔离／质量。

独立过载测试让一个用户同时发起 **68** 个长请求：保持 2 个已产生内容的活跃流，
填满 64 个排队位置，并实测 2 个带 `Retry-After` 的 HTTP 429。此时第二用户的
短请求仍成功。随后主动关闭本次全部活跃和排队连接，验证首个用户可恢复，
并读取新的原生 capture 确认请求、退休和页占用归零。

| 检查 | 原生 Q8 | Tensor Core |
| --- | --- | --- |
| 场景结果／总耗时 | passed / 2.09 秒 | passed / 1.93 秒 |
| 429 拒绝／主动取消 | 2 / 66 | 2 / 66 |
| 第二用户完成延迟 | 0.92 秒 | 0.81 秒 |
| 首个用户恢复延迟 | 0.24 秒 | 0.26 秒 |
| 新增原生 FINISHED_ABORTED 记录 | 2 | 2 |
| 最终空闲页／总页 | 1137 / 1138 | 1075 / 1076 |

66 个取消包含仍在排队的请求，不能算成 66 条 GPU 生成。原生路径的完成诊断
列表已达到 256 条上限，因此 `native_completed_delta=0` 是有界列表长度不变，
不是没有完成／取消事件；此处使用 abort 记录变化和最新资源状态作为证据。
统计脚本随后改为使用累计完成计数和新增记录序号，以适应保留列表滚动淘汰；
补充了回归测试，并再次通过 Tensor Core 实机过载检查（1.97 秒，新增完成 4、
其中 abort 2），证据为 `admission-tensorcore-final/results.json`。

证据：`functional-fixed/results.json`、`functional-tensorcore/results.json`、
`admission-native/results.json`、`admission-tensorcore/results.json`。
最初的 `functional/results.json` 保留为失败证据：harness 曾把 `PRIVATE_1`
当作 `PRIVATE_10` 的外用户标记前缀。已改为定宽、带结束符的标记及完整标识符
边界检测，补充 12 用户回归并重跑；通过结论只引用修正后的报告。

## 短会话恢复与 134K 精确续接

两条路径使用同一 **4096-token** 输入，实际导入 **3072 token** checkpoint。
各自的冷控制、建会话与恢复请求生成的 64 个 greedy token 完全一致；
页被邻居请求复用后仍可恢复；改变前缀后的会话输出与对应冷重算一致。

| 路径 | 建会话耗时 | 恢复耗时 | 本路径 64-token 一致性 |
| --- | --- | --- | --- |
| 原生 Q8 | 14.58 秒 | 4.61 秒 | 通过 |
| Tensor Core | 5.61 秒 | 2.30 秒 | 通过 |

**原生与 Tensor Core 的冷控制输出本身不同。** 上表的一致性是每条路径内部
恢复前后的一致性，不是两条路径的数值或任务质量等价。
证据：`session-short/results.json`、`session-short-tensorcore/results.json`。

**134K Tensor Core 会话精确续接已通过。** 使用冻结的 **134067-token** 输入，
冷建会话耗时 **187.90 秒**；邻居请求复用页后，恢复实际导入 **133120 token**，
完整恢复请求耗时 **5.52 秒**，输出的 **64 个 greedy token ID** 与建会话时
完全一致。证据：`session-long-tensorcore/results.json`；输入 SHA256 为
`8e5ea601d0bb63892e16938e061265ac650d36ef8a5fd20517e3c6b917057a6b`。

本次长输入采用 reuse-only gate：报告明确记录
`independent_cold_control=false`、`changed_prefix_check=false`。
它验证该输入的建会话／恢复续接，不含独立无会话冷控制或长输入改前缀对照；
服务模式也未保留详细 refresh trace，因此不以该结果宣称压缩路径已完成验收。
187.90 秒与 5.52 秒是本次两次完整请求的观测耗时，不是通用加速比、纯 decode
吞吐或长期任务质量结论。

补充的**双用户 134K 生命周期与命名空间测试通过**。两个不同 API key 同时提交
相同输入，并故意使用相同可见 session ID、request ID 和 cache salt。首次两请求
均冷算（session hit 增量为 0），实际同时存在两个 active authority，合计历史
达到 268246 token；并发恢复时恰好增加 2 次命中、导入 266240 token。首次请求
各约 407 秒，恢复分别约 12.03／11.54 秒。清除本次两份会话后，原生请求、退休、
reservations 和 owned blocks 均归零，可用页恢复为 1075/1076。

**这两条并发请求的冷算与恢复输出均未逐 token 一致。** 该项只通过生命周期、
独立会话命中和资源回收检查，没有通过输出一致性验收；不能据此声称多用户长任务
质量已验证，也尚不能将差异全部归因于浮点舍入。逐项核对发现每条输出仅有
1/64 个 token 不同：第 6 个 token 从 `issues` 变成 `errors`，其余 63 个相同；
详情保存在 `long-pair-tensorcore/token-differences.json`。
此次未测五个长请求造成的页容量
排队，也未测试长请求排队／刷新期间的取消。
证据：`long-pair-tensorcore/results.json`、两阶段 observations 和
`run_long_pair.py`（输入及脚本哈希保存在结果中）。

## 适用范围与后续验收

该版本适合在已测机器和固定模型上进行受控多用户试用，默认监听 localhost。
多进程、多副本、多 GPU 的共享配额与公平性未实现；目前公平性按请求准入，
不提供 token、时间、存储计费或跨请求 I/O 配额。全进程 RAM 总量仍没有统一字节准入。
长请求可能在原生等待队列中造成队头阻塞；入口的 120 秒排队超时只覆盖进入引擎
之前的等待，不能作为完整响应时限。空闲会话检查点使用共享 LRU，没有每用户
存储保留份额，客户端每轮仍需提供完整对话。

仍需完成长期混合长短请求、多用户增长会话、decode 中压缩刷新及其取消、
GC／存储配额压力，以及实际 agent 任务正确率和超时对照。单卡最多 8 条准入
序列和 4 个会话 checkpoint 的配置不能据此扩展成无限历史或无限在线用户。
本次短输出检索与吞吐通过也不撤销历史 agent 失败／中断结果。

后续应按业务可接受的 TTFT 和任务成功率选定配置，再进行持续负载与完整任务集
验收。Tensor Core 的收益已经在本次条件下观测到，但输出变化尚待任务质量验证，
因此继续保持显式开启。支持边界见 [support.md](support.md)。
