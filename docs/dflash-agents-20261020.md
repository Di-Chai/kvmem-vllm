# DFlash2 with attention statistics and live agent tools, 2026-10-20

Status: the planned-state qualification, original MTP4/DFlash7 pair and
targeted larger-KV DFlash window pass their execution/lifecycle gates. At GPU
utilization .72 DFlash2 is slower. With DFlash's GPU KV pool enlarged to .80,
observed native generation throughput is **202.64 vs 173.05 token/s (+17.10%)**
and completed-response output throughput is **186.80 vs 150.85 token/s
(+23.83%)**. The latter is a single follow-up against the original MTP
reference, with extra device memory, different graph modes and changed
trajectories; it is preliminary deployment evidence, not a repeated causal
speedup or full task-quality acceptance. Experimental DFlash planning was
default-off during this screen. Following the user's subsequent request, the
default direct agent deployment now explicitly selects the larger-pool profile;
see the adoption note below.

## Experimental compatibility scope

The four attention-maintenance optimizations remain enabled in both arms.
Native FlashInfer/XQA QK reuse is off. This experiment adds an explicit,
default-off direct-launch option, `experimental_dflash_query_planning=true`.
It permits DFlash2 k=7 with FULL CUDA Graphs, synchronous refresh/restore,
no guided Query and the existing qualified 2,048-token target recent band.
Compiled DFlash, asynchronous DFlash refresh, rolling windows and extended
logical position tables are not enabled by this change.

The original DFlash2 contract continues to verify native source hashes, its
five independent BF16 sliding-attention layers, cache layout, logical positions,
lookahead, APC-off configuration and synchronous batches. No native vLLM file,
attention kernel, target scoring formula, acceptance sampler or draft weight
is changed. The target Query/pressure pipeline already maintains the logical
draft frame separately from the selected target frame.

Commit `0d8dee3` contains the experimental launcher and qualification changes.
Commit `b88eb3e` contains the frozen live-tool comparison and correct method
metadata for the existing first16 coordinator. The original MTP launch defaults
and all four overhead-optimization defaults remain unchanged.

## Live-tool comparison protocol

`scripts/benchmark_dflash_agents.py` freezes the current serving source and
extension, full input/profile hashes, the prior state qualification, original
first16 instructions, image identities, protocol adapter and agent binary.
Both jobs execute the original Claude Code loop and real tools in fresh owned
containers. Tool observations are generated by execution, not replayed.

Order is declared before results: MTP4, then DFlash2 k=7, one fresh worker per
arm, eight agent workers, one 300-second formal window per arm. Initialization
uses the same complete 67,584-token fixture and is excluded from the formal
window. The formal window includes container/tool/client waiting, prefill,
Query/pressure work, generation and history maintenance. Unfinished attempts
are censored and receive no invented task score; there are no automatic retries.

Both use the same NVFP4 target, FP8 target KV, K36864/G16384, B32,
100,000,000,000-byte CPU history budget, 4 GiB checkpoint payload budget,
32 session slots, chunk1024, complete accepted history, no historical SSD,
V2 multi/alpha .2 graph pressure and the same attention sampling policy.
Both configure a 2,048-token recent band and synchronous refresh/restore to hold the
target policy fixed within the compatible pair. The logical limit is 262144;
context-limit outcomes stay visible without trimming or recomputing history.
The graph-pressure path retains its own existing mask/mandatory logic; the
configured recent band is not a claim that every graph selection includes it.
Backing-store history capacity remains 524288, above the stricter logical
bridge/model cap. No request in these windows reaches that cap; these are
natural agent contexts, not eight full 256K-input/16K-output requests.

MTP4 uses its supported compiled mode; DFlash7 uses FULL CUDA Graphs and its
separate BF16 draft sliding KV. The atomic Query cap is the same 16384 tokens;
native verifier capacity is 16424 versus 16448 because speculative widths
differ. This is a deployment comparison, not an isolated speculative-algorithm
or four-optimization ablation. The common recent/synchronous settings differ
from the earlier attention-overhead C8 experiment, so its rates are not reused
as a matched baseline.

interval, so no common-eight pure-decode token rate is inferred here.

Completed-response output throughput changes **-13.31%**; the native generation
counter rate changes **-20.91%**. The latter includes accepted tokens from
unfinished requests and therefore differs from completed-response accounting.
The prefill rate is a wall-window mixed-workload rate, not isolated prefill
capacity. Native counter observation spans are 299.55 and 299.17 seconds.

DFlash accepts more tokens per sequence verification, but that does not offset
its total serving cost in this pair. Both execute pure decode steps with eight
requests, with different batch/context distributions. Mean pure-decode step
times are 41.71 and 53.34 ms; these are speculative steps, not per-output-token
latencies. Waiting, kernel/mode cost and changed trajectories all contribute;
the data does not isolate their individual effects.

Both windows end normally with all eight started tasks censored by the
300-second limit. This is real agent execution, but not a completed first16
quality evaluation. Formal API errors, context-limit errors and preemptions
are zero. Cleanup errors are zero and all owned GPU processes/networks are
removed. No unrelated container is stopped.

The four optimizations execute in both arms: native decode commits 14,298 /
9,711; fused scorer calls 6,117 / 6,726; native graph reports 141 / 138. Native
versus Python decode fallback and reference-scoring fallback counts are zero.
Pinned pools reuse slots 4,378 / 4,048 times with zero exhaustion/quarantine.
These counters include initialization. Cold startup contains four / one
caught FlashInfer autotuning OOM tactic fallbacks; formal requests do not fail.
Cold timings include first-use compilation, tuning and execution-order/cache
effects and are not a DFlash cold-start speedup claim.

## Targeted GPU-KV follow-up

The original DFlash geometry has ten recurrent speculative groups, four target
full-attention groups and one draft sliding group. Its conservative joint
reservation includes K/G/lookahead rather than only currently occupied pages.
Its 1,389 rejections are scheduling attempts, not failed API requests; with
no preemption, a waiting request can still reduce useful parallelism.

The follow-up changes only DFlash `gpu_memory_utilization` from .72 to .80,
keeping K/G, history budgets, graph/scoring policy, native grouping, mode and
state guards. It reuses the completed original MTP reference and is explicitly
not another interleaved pair. The declaration is frozen in
`live-tools-more-kv-r1/targeted-plan.json`; the older static manifest sentence
"No historical result is reused" predates this follow-up and is superseded
by that explicit reference/plan. Native KV grows from 1,140 to 1,382 blocks,
38,476,185,600 to 46,643,937,280 bytes.

| Metric | Original MTP4, GPU .72 | DFlash2 k7, GPU .80 |
| --- | ---: | ---: |
| Completed-response output tokens / 300 s | 45,254 / **150.85 token/s** | 56,040 / **186.80 token/s** |
| Native accepted generation counter / observed wall s | **173.05 token/s** | **202.64 token/s** |
| Public prefill counter / observed wall s | 2,159.76 token/s | 1,871.44 token/s |
| Completed model responses / formal tool calls | 201 / 279 | 228 / 318 |
| Mean speculative acceptance length, bonus included | 3.673 | 4.402 |
| TTFT p50 / p95 | 1,159 / 8,313 ms | 1,123 / 9,300 ms |
| Finished-response generation p50 / p95 | 3,508 / 20,296 ms | 3,345 / 21,919 ms |
| Sampled device-memory peak | 74,196 MiB | 79,654 MiB |
| Native KV capacity / grouping | 42,253,254,656 B / 4 | 46,643,937,280 B / 15 |
| Final cumulative GPU reservation rejections | 0 | 0 |
| Mean native waiting-request gauge | 0.003 | 0 |

| CPU history authority maximum | 24,307,695,616 B | 20,314,062,848 B |

| Cold preparation, before formal clock | 933.25 s | 84.45 s |

Relative to original DFlash .72, completed-response throughput increases
**42.85%** and native generation rate **48.05%**. Reservation rejections fall
from 1,389 to zero, and pure decode steps at eight requests increase from
16/1,000 (1.6%) to 683/1,342 (50.9%). This supports capacity contention as a
material contributor to the original result; the closed-loop task mix and
acceptance lengths also change, so it does not isolate a causal percentage.

Relative to MTP4, the useful deployment tradeoff is **+17.10% native generation
rate, +13.43% completed responses and +13.98% formal tool calls**, with sampled
device peak **+5,458 MiB (+5.33 GiB)**. The follow-up uses 7,204 MiB more peak
device memory than the original DFlash window. Public-prefill wall rate remains
lower and p95 response timings are not improved. No pure common-eight decode
token rate is reported: the follow-up also lacks a complete eligible telemetry
interval with eight known ready decoders and no public prefill.

The follow-up native counter interval is 299.13 seconds, with 60,615 generated
tokens versus 56,040 tokens in completed responses. All eight attempts are
again window-censored. API/context-limit errors, preemptions, native decode or
reference-scorer fallbacks, pool exhaustion/quarantine and cleanup errors are
zero. Native decode/fused scoring/native V2 calls are 13,800 / 8,118 / 180;
pinned pool reuse is 4,950 with 1,339,392 bytes retained, below its 64 MiB cap.
Cold startup has one caught autotuning OOM tactic fallback and uses existing
compilation/tuning caches, so its shorter preparation time is not attributed
to the larger pool or DFlash alone. All owned resources are released.

## Default deployment adoption

After reviewing these measurements, the user requested adopting the larger-pool
DFlash configuration as the default. Direct `serve` now uses the bundled profile
when `--config` is omitted; `examples/serve-default.json` is its editable JSON
counterpart. It exactly preserves the measured DFlash .80 resolved profile
except the listener/model-name fields (127.0.0.1:8000, `kvmem`). Query planning,
K/G, recent band, scoring, graph propagation, CPU/session budgets, prefill chunk,
reasoning-end configuration, instrumentation and all four optimizations match.
The bundled Python module is included with ordinary package code, so installed
launches do not require a checkout or benchmark execution records.

This default profile explicitly sets `experimental_dflash_query_planning=true`.
The low-level profile-field default remains false, all compatibility guards
remain enforced, and explicitly supplied profiles retain their settings. The
separate authenticated elastic gateway is not switched to this direct-serving
configuration. This adoption records the user's choice and does not change the
raw experimental evidence, single-window limitations or task-quality scope.

Adoption verification: **270 passed, 1 skipped** in the launcher, draft-contract,
graph-qualification, session and real-agent client regression group. The
no-config CLI works from another working directory without importing torch or
vLLM in dry runs, default profiles do not share mutable state, and an explicit
MTP profile bypasses the default. A dry run with this host's real model paths
matches every field of the measured DFlash .80 resolved profile except port and
served model name. No new throughput run is needed for this profile selection
change; the original GPU evidence remains unchanged. The adoption record is
`docs/benchmarks/dflash-default-20261020.json`.
