# FPS-4：预算内邻块成组选取与成本优化

本次延续 `query_score_mode=key_fps_4`，分别增加两个默认关闭的开关：

- `query_fps_halo_blocks=1`：按原始逻辑位置将命中块与左右各一个连续块作为候选组。
- `query_fps_optimized=true`：只读评分层 K，GPU 构建代表 Key，并减少评分前的 CPU 转换与重排。

两者可单独切换；不改变 32-token KV block、K/G 预算、固定保留、原始 Query、prefill 累计 attention。当前资格范围限定于 FPS-4、Query 图传播 alpha=0。

## 成组选页语义

每个 block 都可作为 anchor，组分数为该 anchor 的原 FPS-4 种子分数。原生 C++ semantic-group picker 按分数选择整组；重复块只收费一次，新增块放不下时跳过整组。预算按物理 32-token block 收费，部分尾块也占一块。选完后不追加邻块。

相邻是原始逻辑位置相接，不是物理 slot 相邻，不跨历史空洞；已有消息边界元数据时也不跨消息。不能完整归属于单条消息的 block 只保留自身组。没有消息元数据时采用连续逻辑历史。固定保留仍由原生 picker 决定。

预览、证据导出及实际提交绑定相同选页集合；历史读取准入重试若改变集合，在 assembly 前拒绝，不留下半更新状态。失败尝试可留下失败证据，但不能成为成功结果。

## 成本优化语义

旧实现逐页读取完整 KV、复制和转换，再在 CPU 构建四个代表 Key。新实现从归档直接读取评分层 K 到有上限的批量缓冲区，排除 V 和 MTP 层；读取期间保留带 generation 的生命周期保护。

本次实测为纯 CPU archive。上述字节计数是交付评分器的请求区间：若用于 NVMe archive，底层 region miss 仍可能读整条 KV record 后再提取 K，不能将 `value_read_bytes=0` 解读为通用的磁盘 V 读取为零，也不能直接外推本次加速。

只读复核还发现非本轮使用的 `CachedArchive._gather_region` 缺少 `MemoryArchive` 已有的 executor 提交异常排空保护；“任务入队后 submit 抛出”的故障需要另行核验和修复。本轮未修改该既有后端，不把纯 CPU archive 资格外推到 NVMe/cache 混合后端。

GPU 仍执行原 FP32 直接平方距离 farthest-first：首个选最大范数，之后选距已选集合最远的真实 Key。未归一化 Key，不改成聚类中心。CPU/GPU 归约顺序可能影响接近相等的 argmax；候选间隔落入保守误差界的 layer/block/head 整组回到 CPU 原算法，保留原始位置的 tie-break。非支持的类型明确回退。

评分先搬运紧凑 FP16 代表缓存，再在 GPU 重排、转 FP32；保持原先每层、每 Query token、每 Query head 的代表 max → block softmax → 层/头平均 → Query 求和。缓存仍计入共享预算，临时 GPU 缓冲区上限 512 MiB。

## 组件验证

固定真实 0011 的原 FP8 K/Q：全部 2,095,616 个代表索引和 Key 字节完全一致；页分数逐位相同，原生单块 picker 相同。GPU 归约守卫回退 9,647/523,904 组，约 1.84%。

同一批固定操作数，旧评分 6.654 s，优化评分 0.250 s；读取、构建、发布并额外校验约 7.747 s。构建 CUDA 分配峰值约 192.1 MiB，优化评分约 355.0 MiB。这是组件测量，不是运行中模型的整请求加速；旧、新评分为相同操作数直接比较。

证据：`artifacts/key-fps-optimized-component-20261023-r1.json`，附源码快照、输入哈希、环境、复跑命令；脚本 `scripts/benchmark_query_key_fps_optimized.py`。实测后仅增加了 FP16 暂存的静态预算记账，算法未改。

组选择、事务回滚、配置转发、缓存生命周期、优化路径和 controller/分析测试通过；最终合并回归 101 passed / 3 skipped（这三项需显式 GPU 开关，独立 GPU 资格测试已完成）。
