# 固定窗口 agent 调度性能协议

2026-10-16。用户明确将主要验收改为固定时长的 GPU 利用率和吞吐比较，
不再以完成整批 DeepSWE 为性能测量边界。定时入口为
`scripts/benchmark_timed_agents.py`，负载为 `scripts/timed_agent_workload.py`；
逐 public batch 观测为 `src/vllm_kvmem/work_counters.py`。窗口、退休屏障、
流式计数及观测相关 35 项 CPU 测试通过，报告为
`artifacts/timed-agent-cpu-20261016.xml`。首对 GPU 诊断已完成，结果在
`artifacts/timed-agent-20261016-r3`：有效输出 85.32 → 89.05 token/s，
提升 4.37%，只有一对，**未达到 10% 目标**。不能用中途高吞吐片段替代此结果。

## 目标与固定条件

主目标是提高相同外生负载下的有效输出 token/s。GPU 利用率用于解释结果，
增加无效重放或重复搬运不能算有效收益。

固定 NVFP4、FP8 KV、MTP(4)、编译图、K128K/G128K、最多四路模型执行，
CPU 历史预算 100,000,000,000 字节。两组使用相同逻辑会话数、输入和工具
计划、生成长度计划及种子。历史不落 SSD，不因容量压力截断或重算。

先比较已有 A0 与 P1；观测代码必须两组相同。原生 vLLM 内部执行策略不在
本轮主动优化范围。已有逐字节恢复及生命周期证明，在相关代码未变时保留。

## 负载

从已有 DeepSWE 记录冻结初始历史、工具新增输入、生成长度和工具等待计划，
保留来源与哈希。每一轮追加该轮自身实际接受的输出 ID，不能用记录中的旧
回答替换新生成的回答。固定生成长度回放用于性能测量，不代表 DeepSWE 解题
质量；后续完整 token 内容也不能声称在 A0/P1 间完全相同。

首对诊断先复用 r6 已验证的控制负载：四个独立会话、141870-token 初始输入、
每轮真实生成 1024 token、固定工具追加序列、每个脚本任务八轮，预热两轮。
每个用户有不同前缀，原生跨请求 prefix cache 关闭。该负载用于先核对新计数
和冷恢复／驻留收益，属于控制实验；DeepSWE 轨迹来源的场景验证另列，不能
把这个首对称为原始任务回放或质量成绩。

DeepSWE 来源的四用户计划已冻结在
`artifacts/timed-agent-deepswe-first4-trace-20261016-v1.json`：按原 manifest
顺序取前四题，在逻辑输入首次达到 131072 token 且后续八轮完整的位置开始，
不按奖励或运行速度挑题。新规范渲染的初始输入分别为
131672 / 131298 / 131201 / 131626 token；每轮输出配额为 91–5593 token。
`scripts/freeze_timed_agent_trace.py` 保留原记录、协议和 tokenizer 指纹，
入口自动识别 `agent_plans`，原样使用每个用户的输入、Query、必留内容和
逐轮输出配额，不套用合成负载的统一输入长度或输出长度。

记录中的等待为“上一模型响应处理完成到下一请求到达”的间隔，包含客户端、
工具及回传开销，不能当作纯工具执行时间。工具结果是固定外生输入，不会随
新模型的工具选择改变；该回放只验证性能，不能替代 on-policy agent 质量测试。
计数、轨迹冻结和消费相关 64 项 CPU 检查通过，报告为
`artifacts/timed-agent-cpu-20261016-trace.xml`。

同规则的 16 轮扩展为
`artifacts/timed-agent-deepswe-first4-trace-20261016-v2-16turns.json`，初始输入、
Query 和前八轮均与 v1 完全相同，60 个追加转换通过检查。保留原等待，最长
179.63 秒，没有为利用率截短等待。32 轮扩展不成立：首题从首次达到门槛
到自然结束只有 17 轮，已明确拒绝生成，没有换题或另挑片段。

分别测两个供给条件：

1. 持续供给：工具数据预先准备，维持有候选请求，观察服务容量。
2. 工具等待：使用相同冻结工具等待序列，观察实际等待节奏下的跨轮收益。

两组逻辑会话数及补位规则相同；模型执行上限始终为四。记录就绪队列是否
为空，区分供给不足与有工作却无法推进。会话数必须满足 CPU 历史容量约束。
使用预先定义的有限脚本任务循环时，仅在脚本任务正常结束后清理并补位，
清理和新任务初始 prefill 属于持续负载的一部分。不能临时缩短历史维持吞吐。

## 预热和测量边界

两组完成相同预热工作量和轮数，建立相同历史长度及阶段分布；不能按各自跑
两分钟预热，因为快组会进入更长上下文。驻留状态允许不同，这是待测机制。

预热请求及其发布 fence 完成后确定单调时钟区间 [T0, T0+300s)。整个窗口
作为分母，包含 prefill、decode、恢复、维护和工具等待。窗口结束停止新供给，
正常收尾与最终清理另计；不要求请求完整落在窗口内。

所有窗口内接受的输出都计入，包括结束时尚未完成的请求。记录末尾在途
请求、未完成工作、等待年龄和响应时间删失，不能只保留完成请求或满批片段。
客户端到达计数与原生计数边界不同，分别注明时间范围，不要求伪造逐 token
完全一致的窗口差值。

## 指标及计数来源

| 指标 | 计数规则 |
| --- | --- |
| 有效输出 token/s | 窗口内已接受输出；排除拒绝的 MTP 草稿；原生计数与流式输出 ID 交叉核对 |
| 实际 public prefill token/s | 按实际 public batch 的 prompt 位置执行数累计；排除恢复历史、padding 和越过 prompt 尾部的 lookahead |
| 内部 Query 工作量 | query、guided_prompt、guided_decode 分开计数，注明提交或完成边界 |
| GPU 利用率 | 固定一秒采样，报告时间加权均值、分布、低利用率比例和采样缺口；不能称为 SM occupancy |
| 实际模型并发 | public batch 的 prefill/decode 请求数和上下文分布；scheduler running 数不能代表同时 decode 数 |
| 恢复 | 热命中、上传字节、排队及准备时间、服务时间、总时间；host gather 已包含在服务时间内 |
| 延迟 | 输出事件间隔 p95、请求平均 TPOT、TTFT；MTP 一个事件可以包含多个 token，事件间隔不是单 token 延迟 |

现有 `prompt_tokens_total` 包含恢复历史；`local_compute` 虽排除缓存，却在
首输出时集中入账。因此它们不能直接充当固定窗口内的实际 prefill 计算量。
现有 `model_step_latency.jsonl` 是采样，也不能外推精确总量。

新增 public 计数应位于真实执行路径、逐批次累计；最终 prefill 步按剩余
prompt 长度截断，避免把 MTP 额外位置计作 prefill。私有 Query 路径独立记录。
内存累计、低频发布，不逐步同步 GPU 或逐步写大日志。若采用提交计数，需要
明确边界可能包含尚未完成的 batch；完成计数使用异步 fence，保留观察误差。

原生 accepted generation 计数来自 `new_token_ids`；原生输出事件延迟为
EngineCoreOutput 间隔。统计前检查引擎身份、计数重置、预检/清理排除和缺样。
vLLM 的 Triton JIT 警告按内核名 `warning_once`；窗口内没有新增警告不能
证明完全没有新的 specialization 或编译，不从警告条数外推精确编译次数。

## 优化与重复确认

先做持续供给 A0/P1 各五分钟的一对诊断。结合就绪空档、实际并发、CPU gather、
恢复上传、内部重放及模型步时间，确定主要损失；只修改有证据指向的一项。
必要时做针对性的单项消融，不同时扫描并发、MTP、prefill chunk 等参数。

有明确收益和对应机制后，按 AB、BA、AB 补成三对。沿用主要吞吐关卡：三对
均改善、中位提升至少 10%，且无正确性错误、容量死锁或长请求饥饿。延迟变化
独立报告；离线吞吐提升不能自动宣称满足 SLO。

工具等待条件先测一对；需要宣称该条件稳定改善时再补齐三对。首次持续供给
三对共三十分钟有效测量，两种条件全部三对共六十分钟；模型加载、预热和
收尾另列。任务质量另做回归，不混入此处的固定窗口吞吐。

## 当前单项优化

首对 A0 的 26 次 CPU 恢复上传 201.16 GB 历史 KV；P1 的 25 次驻留恢复
不上传历史 KV，仍恢复约 158 MB/次的模型状态。恢复服务中位数从 2.77 秒
降到 0.067 秒。P1 更早进入新脚本任务，因此窗口内新增初始 prefill 和
T1 在途工作不同；这些工作照常保留在窗口，不能将 prefill 增量称为 decode 收益。

代码检查发现 `cpu_gather_workers` 仅接入 NVMe 读缓存，CPU authority 没有使用。
完整 record 读取在 Python 下持 tier 锁复制，局部 record 路径已有单线程原生
gather。修复为借用 immutable record 引用后解锁，使用已有释放 GIL 的原生
复制函数，并接入原有 worker 数；大批次使用独立有界线程池，失败后等待所有
复制任务退出才释放租约和目标缓冲区。不新增产品配置，也不更改评分和历史内容。

单项对照目录为 `artifacts/timed-native-gather-20261016-r2`。两组均固定
A0 冷恢复策略；只有服务端 `memory_storage.py`、`storage.py` 不同，共用
冻结客户端、模型配置和负载。先执行真实模型四用户冷恢复、压力回收的逐字节
校验，通过后才运行各 300 秒窗口。该对照只检验 CPU gather，不能冒充 P1
调度策略收益。相关 CPU archive/runner 检查 92 项通过；r2 的真实模型
冷恢复及压力回收共 16/16 次恢复通过逐字节校验，报告为
`correctness/restore-gate.json`。两个 300 秒性能窗口均已完成：

| 指标 | 旧 CPU 读取 | 原生并行 gather |
| --- | ---: | ---: |
| 有效输出 token/s | 87.50 | 91.16 |
| GPU 时间加权利用率 | 72.06% | 80.34% |
| CPU 准备中位秒数 | 2.409 | 1.617 |
| 恢复服务中位秒数 | 2.682 | 1.832 |

首对有效输出提升 4.175%，**未达到 10% 目标，也未形成三对稳定收益结论**。

四用户正常收尾。CPU 准备包含装配提交等其他工作，不能把表中耗时叫纯 memcpy。

不同，prefill 增量不能算作 decode 加速。
