# 长上下文与 32 客户端吞吐：2026-10-13

**主实验、同输入复测及八请求配置对照全部完成，共 13 批、130/130 请求成功，
输出 133120 token。**
32K 的共同稳态 decode 总吞吐为：单路首测 **38.17**、复测 **47.22**，
4 路 **121.00**、8 路 **154.74 输出 token/s**。64K、134276-token 单路分别为
**52.34、44.37 token/s**。短输入与 32K 的 32 客户端请求都全部完成，但均通过原生
容量排队执行，没有测得 32 路共同 decode 窗口。八请求配置处理同样 32 个短请求的
整轮吞吐为 **249.95 token/s**，高于 32 请求配置本轮的 **203.85 token/s**。

本轮没有修改推理内核或降低上下文预算。它测量扩大服务准入后的能力和限制；不将与旧配置、
旧输入之间的数字差异直接归因于代码优化。

## 实验配置

单张 RTX PRO 6000 Blackwell，目标模型 Qwen3.8-27B Q8_0、目标 FP8 KV，
独立 **DFlash2 BF16 草稿模型，7 个 speculative tokens**。这里使用的是 DFlash2
推测解码，**不是目标模型的原生 MTP 路径**。保持 eager／同步调度、单卡单 worker、
`q8_tensorcore=true`，KVMem 参数为 K131072／G65536／B128，最大模型长度 262144。

主实验 profile 将 `max_num_seqs` 和 API `max_inflight` 均设为 32，
`gpu_memory_utilization=0.80`；每用户最多两个请求，不同并发客户端使用不同 API key。
批次 token 预算为 4224，长 prefill 每请求最多 1024 token，`prefill_cadence=8`。
共享 CPU 读缓存上限 16 GiB，启用 packed assembly、直接 pinned 读取及异步归档退休。

对照实验保持 `gpu_memory_utilization=0.80` 和相同模型、K/G、DFlash 设置，将
`max_num_seqs`、API `max_inflight` 均设为 8。其启动 KV 预算为 **41.42 GiB**，
物理池 **1317 页**、初始可用 **1316 页**；主实验对应为 41.38 GiB、1316／1315 页。
对照完成后实验服务保留八请求准入配置，健康检查返回 200。

这些仍是实验配置，**没有将该实验设置写入默认示例配置**。通过这些隔离负载，不等于通过任意长短混合流量、
长期满负载、故障恢复或高显存利用率生产资格验证。

实际 14 路的有效区间，计时口径与上表完整 C1／C8 共同窗口有所不同，不能填入

## 八请求配置对照：仅短输入

重启 worker 后，使用相同 152-token 输入、1024-token 输出和测量脚本，先执行
C1／C8 作为同输入参照和预热，再执行 C32。三批共 **41/41 请求成功**：

| 客户端数 | 成功请求 | 共同稳态 decode 总吞吐，tok/s | 整轮吞吐，tok/s | 整轮耗时，秒 | TTFT p95，秒 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1/1 | **60.316** | 56.724 | 18.052 | 0.594 |
| 8 | 8/8 | **269.837** | 247.006 | 33.165 | 1.828 |
| 32 | 32/32 | 不适用：没有 32 路共同解码窗口 | **249.947** | **131.100** | **100.044** |

两套配置的 C1／C8 共同稳态吞吐差异均小于 **1.1%**。在 C32 服务负载下，八请求
配置的实际 owner 数最高为 **8**，其余客户端在入口容量队列中等待；主实验则让请求
进入原生 scheduler，再由页预算限制到最多 14 个短请求 owner。

本轮八请求配置的 C32 HTTP 吞吐相对主实验的 **203.850 token/s 增加 22.61%**，
整轮耗时从 **160.746 秒降至 131.100 秒**，TTFT p95 从 **131.585 秒降至
100.044 秒**。这说明扩大活跃请求数并不保证服务吞吐提高，八请求配置在这个短输入
工作负载中表现更好。

严格离线分析中，对照的 **8-owner** decode 区间累计 **79.400 秒**，SSE 吞吐
**274.509 token/s**，占整轮 **60.565%**；主实验的 14-owner 区间为 85.464 秒、
246.266 token/s，占整轮 53.167%。两者分别使用各自实际 owner 稳定的有效区间，
没有覆盖完整服务过程，也都不是 32 路共同 decode 结果。

两套短输入配置均按 C1→C8→C32 执行，各档仍只有一轮，且经历重启和不同运行时段，
不能将差异概括为普适因果收益。
**未测量八请求配置下的 32K C32 对照**，上述提升不能外推为长上下文的收益。

## 同输入复测与运行阶段影响

32K 首测与后续单路复测使用完全相同的输入文件 SHA-256，生成的 **1024 个输出
token 的 SHA-256 也完全相同**。稳态速率仍从 **38.166** 变为 **47.218 token/s**，
约增加 **23.72%**；TTFT 从 55.48 秒降为 38.65 秒。

严格采样区间中，每次原生验证调用接受的 token 约为 **2.655／2.653**，基本不变；
每秒调度的验证调用从约 **14.28** 变为 **17.69**，增加 **23.88%**。
这支持本轮存在运行阶段／状态敏感性，而非用接受长度改变解释全部差异。计数来自
原生调度与延迟更新的归档快照，不是实测 GPU kernel step 时长。

一次复测无法区分预热、分配器缓存、I/O、其他负载等原因。不能把首次 32K 单路与
8 路相除后宣称确定、普适的 4.05 倍增益，也不能因 64K 单路快于首次 32K 就断言
上下文越长越快。跨长度的输入和输出不同，测量顺序也不同；本文保留两次单路结果，
不把它们合成有统计代表性的均值或置信区间。

## 输入与计数方法

短输入是要求连续撰写多用户推理服务设计评审的技术写作提示，通过 chat/completions
提交后实际为 152 token。长输入使用本地固定技术材料作为背景，再加入新的工程设计
评审写作问题；**属于 synthetic 派生性能输入**，不是原始 agent 任务的完整质量评测。
背景中的工具调用和结果只是文本，不执行工具。

32K／64K 输入使用原始材料的头尾片段并明确标注中间省略，再保留共同的新增写作问题；
134276-token 输入的**前 134067 个 token 完整保留原始冻结输入且逐 token 相等**，
其后追加新的写作问题及对话边界，未裁剪原有长背景。完整请求因此仍是派生性能输入，
不同于原始任务。各长度档实际输入文件分别是
`synthetic_request_32768.json`、`synthetic_request_65536.json` 和
`synthetic_request_134k_plus_query.json`。

长输入的 token IDs 直接发送到 completions，不额外套 chat 模板；最终 usage 必须等于
输入 token 数。同一长度在各并发档使用相同输入。原始文件、输入哈希、harness 哈希和
每请求输出 token ID 哈希保留在结果中。

采样条件为 temperature=0、seed=104729、固定 1024-token 输出、ignore_eos=true；
提示关闭 thinking，强制输出长度用于性能计数。它不证明模型自然结束行为或答案质量。
主矩阵每档只有一轮，32K 单路另有一次复测，没有置信区间；不同并发的数值路径与
推测接受率也可能不同。八请求配置的短输入对照各档也只有一轮。

稳态测量遵循以下规则：

- 精确累计 SSE `choices.token_ids`，要求每请求计数与最终 usage 相符。没有 token IDs
  的角色或空事件不计数；文本为空但带有 token IDs 时照常计数，多 token burst 按实际个数计数。
- 每个请求裁掉至少前后各 64 token，取所有请求剩余区间的交集。burst 边界可能多裁掉
  一些 token；整个交集内的零进展停顿保留在分母。
- 原生 accepted-history、prefill 计数及 scheduler 快照独立检查 owner 身份、并发进展和
  窗口稳定性。默认要求至少 90% 有效原生覆盖，窗口内部不能出现 prefill、待完成 refresh
  或身份错配；非原子读取跨越窗口边界时列为不确定证据。
- 流式 token 到达吞吐包含调度、DFlash 草稿、验证、采样、归档和传输开销，不是纯 CUDA
  kernel 吞吐。原生归档提交速率有延迟，单独报告，不替代精确 SSE 计数。
- 同时存在并持续进展的 owner 可以支持并发结论，但采样不能证明每个 GPU step 的
  batch 都恰好等于该 owner 数。没有完整客户端共同窗口时，HTTP 服务成功与实际
  owner cohort 成绩分别报告。

离线分析发现，只检查 accepted-history owner 会遗漏一种情况：长 prefill 已持有
reservation，但尚未发布首批 accepted-history，且采样时 prefill 计数暂时未变。
严格分析因此额外要求连续三个快照的 **reservation 数量等于已捕获 owner 数量，
reservation 集合保持稳定**，并继续检查全部 owner 已完成 prompt、流式生命周期和
prefill／refresh 边界。存在隐藏 prefill owner 的整个区间都排除。

本文的 owner cohort 成绩采用 `cohorts-strict-reservations.json`。旧分析文件保留用于
审计，不再作为最终 cohort 成绩。**采集本轮数据的核心测量 harness 未修改**，严格
规则在原始结果上离线复核；相关测量与分析回归 **52 项通过**。这项收紧不将原始
HTTP 成功请求改判为失败，也不重写主表的完整 SSE 窗口。

主实验和八请求对照的首批 C1 各记录 **3 次 FileNotFoundError 原生快照读取错误**，
发生在启动约 0.02／0.27／0.52 秒，均早于各自首个 token 事件约 0.57／0.61 秒，
也早于约 2.31／2.11 秒开始的稳态窗口。错误计数保留在原始结果中，不影响本次有效
稳态窗口的核验；本文不将整场采样描述为零错误。

## 为什么 32 个客户端需要原生排队

主实验启动日志实测 KV 可用预算约 **41.38 GiB**，物理共享池共 **1316 页**，其中一个
是 null page，初始可用 **1315 页**。组结构为十个 GDN 状态组、四个目标 full-attention
组和一个 draft sliding-attention 组；每页约 **32.1875 MiB**。目标原生 block 为
3296 token，draft 为 1648 token，它们都不同于 KVMem 的 128-token 归档块。

在当前模型、批预算和七个草稿 token 下，每请求固定预留 85 页：GDN 的基础状态与
speculative 状态占 80 页，draft 窗口占 5 页。目标 KV 再按完整请求的增长上界预留：

```
request_pages = 85 + 4 * ceil(min(prompt_tokens + max_output_tokens + 16,
                                K + G) / 3296)
```

因此，短输入加 1024 输出需 89 页，上限为 14 个；32K 需 129 页，上限为 10 个；
64K 需 169 页，上限为 7 个；134276 加 1024 输出需 253 页，上限为 5 个。
这些是当前池的页预算上限，不代表已逐项实测到相应并发，也不包含刷新临时张量。

将 API 和 scheduler 上限提高到 32，让 32 个用户进入原生调度器；物理容量不足时仍会
排队。仅将显存利用率提高到 0.90／0.92，也不能让当前布局容纳 32 个短请求：它们的
KV 预算本身就约 89.52 GiB，还要加模型权重和工作区。更高利用率还会压缩刷新临时
状态的余量，不能由本轮结果直接推导出可安全部署的配置。

## 134K 阶段具体验证什么

依据 [admission.py](../src/vllm_kvmem/admission.py) 的 `QueryPolicy.refresh`，
prefill 到达 K=131072 时安装边界窗口；其后尚未完成输入的对齐 chunk 会进行
query-conditioned selection。本轮实际记录了 **4 次 prefill refresh**，对应
history=**131072、132096、133120、134144**。每次选择窗口均为 131072 token；
首次为边界安装，没有执行 provisional probe，后面三次均执行 probe。最后一块
query 为 132 token，与完整 134276-token 输入相符。

随后的 1024-token 输出距离 K+G 工作窗口下一次填满还很远，记录确认 **decode
测量窗口内没有 refresh**。因此 44.37 token/s 是完成上述预填充选择后的解码吞吐，
不包含持续 decode 刷新的成本，也不验证超过 G 的长生成、生成期反复刷新或任意
长短混合流量。

刷新还有页预算之外的临时成本：当前实现为 provisional forward 复制同批请求的
GDN 状态，真实张量约 **1.20 GiB/请求**。本轮 134K 只测单路且与其他阶段隔离，
没有验证大批混合请求下这项开销。GPU 利用率参数也不是运行期物理显存峰值的硬上限。

主实验及复测结束时，`final-server-state.json` 记录 **89 个请求完成**，
scheduler 请求、reservation、owned blocks、accepted-history owner、归档槽、
未完成下载、retiring requests、未完成刷新和连接器任务均为空或零；
可用页恢复为初始的 **1315／1316 总页**。这是本轮完成后的资源回收证据，不替代
长期运行泄漏测试。

八请求配置的 `control-8/final-server-state.json` 单独确认 **41 个请求完成**、
scheduler 请求和全部 owner 清零，reservation、refresh、connector、归档槽、
下载与退休任务清零，可用页恢复为 **1316／1317 总页**，健康检查为 200。

## 预填充优化方向与证据边界

源码确认，Q8 Tensor Core 对大 prefill 和 decode 共用 BM16、split4 的默认路径，
大矩阵产生较多量化 CTA 和 FP32 partial 缓冲。可以单独测试大 M 的量化打包、较大
行块和较少 split，并保持小 M 的 decode 配置独立。捕获与归档也包含 GPU 打包、
CPU 编码和有界异步 I/O，应该分别计时。

旧 M1024 实权重微测中 Tensor Core 比原生 Q8 快约两倍，但没有覆盖当前全部投影和
M4096 长批次。旧短 decode trace 也不能证明本轮长 prefill 的耗时分布。
**本轮尚未 profile 当前长上下文 Tensor Core 路径，也未据此更改 runtime；不把慢
prefill 归因给某个 kernel、PCIe 或磁盘。**
