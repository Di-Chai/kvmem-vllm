# 原生 vLLM 与 KVMem：八并发 agent 分阶段对照

2026-10-16。原生同步、原生异步两组均已完成；KVMem 使用最近完成的八路
默认基线。本次先分别报告 prefill 服务速率和共同 decode 观测速率，再报告
持续供给下的整体效率。单次顺序运行只提供诊断，不能作为已隔离的 KVMem
捕获开销或稳定收益结论。

## 分阶段结果

| 指标 | KVMem | 原生同步 | 原生异步 |
| --- | ---: | ---: | ---: |
| 初始长文 prefill 服务速率，token/s | 3690.17 | 5156.19 | 5164.65 |
| 初始八路全部获得首输出，秒 | 287.00 | 205.40 | 205.06 |
| 八条流共同 decode 观测速率，accepted token/s | 399.86 | 561.14 | 552.54 |
| 纳入共同 decode 的总时长，秒 | 31.18 | 20.30 | 24.23 |
| 纳入共同 decode 的片段数 | 4 | 4 | 6 |

相对原生同步，KVMem 两项观测速率分别低 28.43% 和 28.74%；相对原生异步
分别低 28.55% 和 27.63%。这些差值包含执行路径和运行时成本，decode 还受
各组自身生成内容、MTP 接受率与片段阶段影响，不能直接解释为捕获代码的税率。

**Prefill 定义。** 三组初始八个输入逐 token 完全相同，共 1,059,088 个位置，
每路约 131K～134K。分母从最早请求发起到最后一路首次收到正 token 输出。
这是包括 HTTP、排队、运行时维护、采样以及可能残留的首次形状延迟编译的
服务时间，不是纯 GPU prefill 内核耗时，也不是正式 300 秒窗口的计算计数。
在该区间结束前，没有初始请求完成，没有下一轮预热请求进入。仍有少量先出
首 token 的请求开始 decode：三组分别有 35/84/99 个初始请求输出 token，
另各有七个清理输出。GPU 时间加权利用率分别为 79.10%/99.25%/98.87%，
采样覆盖率均为 100%。

**Decode 定义。** 根据完整请求的正 token SSE 时间线，每个请求首尾各剔除
64 个 accepted token，准确处理 MTP 输出块跨越剔除边界的情况；取八条流
共同处于该区间的片段，只保留至少两秒的片段。累计最终接受的输出，除以
片段总时长。八个生产者此时没有其他公开请求进入 prefill，但仍可能有内部
维护。八条流同时存在不等于逐模型批次均为八路 decode，原生 running=8
也不能证明这一点；因此表中指标明确称为共同 decode **观测**速率。

另有两个 agent/轮次/输入长度完全匹配的共同 cohort，KVMem/原生同步分别
为 401.53/559.05、392.90/574.04 token/s，方向一致。但两组这些请求的实际
输入与输出 ID 哈希不同：各轮追加的是自身新生成的输出，不能为了配对而
替换成旧答案。没有独立控制内容与投机接受率，仍不构成纯内核因果消融。

## 相同配置与原生隔离

两组原生服务直接运行已安装 vLLM CLI，不经过 KVMem 服务包装。禁用插件，
清除继承的 KVMEM/VLLM 覆盖与 PYTHONPATH；保存安全启动清单和原生源文件
哈希。API 进程及可读环境的运行子进程检查通过。EngineCore 的进程标题库
会改写 `/proc/environ`，该进程的缺失字段不能单独作为插件开启或关闭的证据。

共同条件为 Qwen3.8-27B NVFP4、目标与 MTP FP8 KV、原生 MTP(k=4)、V2
runner、编译模式 3 与 FULL_AND_PIECEWISE CUDA Graph，八个原生请求槽，
GPU 比例 0.81、max_model_len=524288、普通 prefill 阈值 2048，TP=1。
实际原生总 token 上限均为 16424，包含包装配置展开后的重放容量；不能将
KVMem profile 中的 4224 直接误认为原生引擎上限。原生组保留 prefix cache、
chunked prefill 和默认 hybrid cache align 策略，分别关闭和开启异步调度。

KVMem 保留原有上下文评分、捕获、历史维护、CPU 恢复、压力驻留与准入，
关闭实验性 prefill 合并，K/G 各 128K、CPU 历史 100 GB、无 SSD 历史。
原始 93 条恢复记录均满足 history_tokens=active_tokens，最长 169954 token，
未超过 K+G 的 262144 容量。本负载没有发生选页截断，不能将结果解释为
KVMem 只计算 128K 而原生计算完整历史。

工作负载为来源清单的前八个独立 agent、每个 16 轮冻结外部消息，逐轮输出
配额为 52～8583 token。每组完成相同的两轮预热后测量饱和 300 秒窗口，
工具数据预先准备；追加各组自身实际输出 ID。每个逻辑 epoch 独立设置 cache
salt，同一 epoch 跨轮不变，避免新任务重复种子从其他 epoch 额外命中。
这是性能回放，不是完整 DeepSWE 工具执行或任务质量验收。

## 整体效率：单独报告

| 完整 300 秒窗口指标 | KVMem | 原生同步 | 原生异步 |
| --- | ---: | ---: | ---: |
| 有效 accepted 输出 token/s | 226.20 | 186.40 | 208.10 |
| 窗口内 accepted 输出 token | 67860 | 55919 | 62430 |
| 窗口内完成请求 | 79 | 56 | 66 |
| GPU 时间加权利用率 | 72.25% | 98.93% | 98.99% |
| 窗口外排空，秒 | 40.15 | 18.74 | 56.21 |

完整窗口包含 prefill、恢复、维护和 decode。KVMem 比两组原生分别多输出
21.35% 和 8.70%，尽管分阶段观测速率更低。不能因此声称 KVMem decode
更快，也不能根据原生更高 GPU 利用率断定它完成更多有效工作。

原生同步在窗口内的首输出集中报告 675488 个实际未缓存 prefill 位置；另有
一个清理位置。agent 3 的 epoch 0/turn 3 与 agent 5 的 epoch 0/turn 12
分别有 142626/169822 位置的同 epoch 完整前缀未命中，外部新增仅 49/1115
位置，两个请求共有 311284 个超出外部新增的计算位置。已逐个重建请求历史，
确认它们沿用相同 salt 并追加自身输出，前缀没有被改写。另有新 epoch 的
131298-token 冷种子，属于正常新任务输入，不能算缓存失败。

原生异步在窗口内集中报告 544595 个未缓存 prefill 位置；末尾还有两个请求
未出首 token，不能丢弃。排空后它们报告的整个请求未缓存输入共 282137
位置，**不是** T1 时刻的剩余计算量：没有逐 chunk 完成进度可以这样归属。
这些集中入账的计数都不是独立 prefill 吞吐能力，也不与上表初始服务速率混用。

KVMem 窗口内 85 次恢复为 82 热、3 冷；冷恢复共上传 20.97 GB 历史，
单次服务约 8.05/11.97/15.13 秒，任务可重叠，不能累加成独占 GPU 停顿。
原生 hybrid cache 需要 attention、recurrent 与 MTP 组共同满足复用条件；
本次未采集逐缓存组淘汰事件，不能进一步断言是哪个组、LRU 淘汰或实现缺陷。
零抢占也不代表没有非活跃缓存页被回收。

## 与此前 800+ decode 的区别

此前 `scheduling-coordination-20261015/v2-live-r6/performance/pair-00-B0`
的八路单轮固定输出测试，输入 32768、输出 4096，获得 818.79 token/s 的
共同 decode；它已开启 MTP(k=4)、Action attention 与 Prefill attention。
另一次 50006-token 输入测试记录 860.71 token/s，但其选页预算、评分开关
和样本不同，不能只按输入长度将两组当成相同配置。

本次 agent 回放初始输入即约 131K～134K，跨轮历史增至约 170K，恢复记录
确认完整历史都留在 active view。K=128K/G=128K 是选择预算与增长余量，
本负载并未将每步注意力强制限制为 128K，更没有沿用旧测试的约 32K 窗口。
长上下文增加目标和 MTP 注意力路径的工作；具体带宽与内核占比仍需 profiler，
不能只凭上下文长度给出精确开销比例。

从保存的逐步记录筛选八路 decode、零 public prefill 的模型步：

| 时序，中位数 | 旧 32K 单轮 | 当前长历史正式窗口 |
| --- | ---: | ---: |
| 步总时序跨度，ms | 39.12 | 75.54 |
| 模型段，ms | 36.92 | 69.98 |
| 模型前维护段，ms | 2.27 | 4.52 |
| 观察步数 | 206（每四步采样） | 1685（每步采样） |

当前共同 SSE decode 片段内部另有 402 个完整八路纯 decode 步，中位模型段
69.49 ms、维护段 4.38 ms、步总跨度 74.86 ms，与全窗口方向一致。模型段
仍包含 target、sampling、MTP 与 capture，维护段也不等于全部 KVMem 成本。
这些是不同负载、不同采样频率的诊断，不能将两段之差视作已隔离的 GPU
attention 内核回退或 CPU 历史维护回退。

当前长历史的原生同步/异步共同 decode 为 561.14/552.54，KVMem 为 399.86。
这表明负载变长后原生路径也不能复现旧短上下文峰值，同时 KVMem 相对当前
原生仍有差距。生成内容、MTP 接受率、评分/捕获、同步与调度成本尚未单项
隔离，不能把全部差距归给某一个组件。旧 32K 已有 attention 评分，也不能
用“现在才开启评分”解释下降。旧 raw-K GPU 加速缓存开启、当前为容纳八路
关闭，配置也有变化；其主要影响恢复装配，没有该开关的同负载 decode 消融，
不宣称它解释了稳态下降。

399.86 的共同区间没有其他公开 prefill 生产者，不能用公开 prefill 阻塞
单独解释它相对 818.79 的下降。226.20 是另外的整窗指标，包含跨轮 prefill、
恢复与维护；这些阶段再进一步降低长期平均输出。原始筛选及文件哈希保存在
新实验根目录 `decode-context-comparison.json`，本轮未重新启动 GPU 测试。

## 后续统一评估口径

离线持续供给的主判据为**完整固定窗口的最终 accepted 输出 token/s**，同时
列出完成轮数、每用户进度、未完成输入与末尾排空，避免只多做长 decode、
推迟 prefill 就被误认为总效率提升。GPU 利用率和峰值只用于解释。

Prefill 与 decode 在主报告中分别保留，不能将输入与输出相加成统一 token/s：

| 维度 | 建议指标与比较条件 |
| --- | --- |
| 初始 prefill | 相同冷输入、相同并发，从发起到全部首输出的服务速率与 TTFT；首次编译单列 |
| 跨轮新增 prefill | 按相同历史长度与新增输入长度分组的恢复后 TTFT、服务耗时；冷热恢复分列 |
| 工作量归属 | 初始输入、新增用户/工具输入、历史重算、内部 Query/guided 工作分列；KV 恢复单列字节与耗时 |
| Decode 执行能力 | 相同实际 decode 批次并发与上下文分布下的 accepted 输出速率；并列 MTP 接受率与每步接受长度 |
| 混合调度干扰 | 每请求 TPOT、输出事件间隔 p95/p99、长时间无输出比例；区分有 ready 工作与工具供给空档 |
| 跨轮复用 | 热命中率、历史重算位置、冷恢复上传量、恢复排队/准备/服务时间 |
| 稳定性和公平性 | 每用户进度、等待年龄、错误/抢占、CPU/GPU 容量等待与窗口末尾删失请求 |

TPOT 按请求用首输出后的时间除以剩余输出 token 数；MTP 一次 SSE 可输出
多个 token，输出事件间隔不能称为单 token 延迟。该区别与
[vLLM 的指标定义](https://github.com/vllm-project/vllm/blob/main/docs/benchmarking/cli.md)
一致。新增输入处理率与实际 prefill 计算率分别命名，历史被重算不能计作新增
有效输入；过往生成 token 首次进入下一轮执行与旧输入重算也应区分。

只有实际采集到的阶段执行计时才能报告纯计算速率。混批中的 prefill/decode
共享模型执行时间，未做额外归因时不能把整步耗时同时独占归给两者。主机
阶段和数据搬运也可重叠，不能将各自时间简单相加成墙钟损失。

当前表中初始 prefill 与共同 decode 已可用；全量逐批 decode 并发条件化、
逐 chunk 原生完成计数与严格内容/MTP 控制尚未纳入本次原生实测，不应在
报告中暗示已经完成。要宣称稳定改善，仍需同条件 AB/BA 重复确认；若以后
评价在线 SLO 模式，再增加符合 TTFT/TPOT 门限的 goodput，本轮不代设门限。

## 证据、验收与限制

新实验根目录：`artifacts/timed-native-vllm-c8-20261016-r1`；KVMem 对照为
`artifacts/timed-prefill-coalescing-c8-20261016-r3/pair-00-A0`。
根目录 `review.json` 与 `independent-review.json` 保存分阶段口径、逐输入
哈希、共同片段、缓存未命中分析及不可变快照复核；`review_evidence.py`
为本轮审计证据脚本。各组 `native-launch.json`、`server.log`、
`saturated/events.jsonl` 与采样记录保留启动配置和原始观察。

原生两组完整 97/108 条流的输入均可由种子、该组自身 accepted 输出与工具
输入重建，输出配额和哈希通过；全程 76148/79504 个 accepted token 与
原生计数精确一致。原生最大 running=8、零抢占，GPU 采样覆盖率均 100%。
启动期间有 NVFP4 自动调优候选显存不足后回退默认 tactic 的日志，服务继续
正常完成，不能把它描述成全程不存在任何 OOM 日志。模型进程均已退出，
`cleanup-audit.json` 确认没有剩余 GPU 作业。

启动器 25 项、原生入口 5 项、共享负载及相关回归 76 项检查通过。没有修改
已安装 vLLM 或为了提升结果改变模型验证逻辑。当前证据只支持单次分阶段
与固定窗口诊断，既不提供真实工具任务准确率，也不宣称稳定因果收益。
