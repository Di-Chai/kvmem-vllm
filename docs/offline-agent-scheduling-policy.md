## 目标和约束

当前只做离线模式：固定一批任务，最小化整批完成时间，提高有效输出吞吐。
GPU 利用率、decode 间隔和满批比例用来解释结果，不单独决定策略好坏。
不为了让曲线平滑而主动降低整批吞吐。SLO 模式以后独立设计。

保持 K=128K、G=128K、最多 4 路原生模型执行，NVFP4 / FP8 KV / MTP(4)、
编译图及现有 MeanK、Query history、attention 评分契约。CPU 历史预算为
100,000,000,000 字节。历史不落 SSD，不因容量压力丢弃或重算。

CPU 准入必须覆盖本轮的历史增长并保留至少一条轨迹的推进空间；GPU 准入
必须覆盖实际 active 及本轮生成的原生页需求，包括 MTP / recurrent 额外页。
闲置缓存不能侵占已经发给活跃请求的未来增长额度。

## 一次调度的决策顺序

1. **发布完成事件**：非阻塞检查 CPU 历史发布、恢复 DMA 和模型状态 fence；
   就绪请求进入后续 batch，未就绪请求只阻塞自身。退休未确认的页不能复用。
2. **纳入所有可运行 decode**：沿用 vLLM 原生连续批处理。准备工作不能让
   已经可运行的请求因为另一个请求未准备好而整批等待。
3. **有计算空位时选择补位对象**：先检查精确跨轮复用；其余候选按完成恢复和
   剩余输入处理所需的预计时间排序。每完成一个候选，就重新评估队列。
   持续被越过的候选获得老化优先级，不能长期饥饿。
4. **取得 CPU 与 GPU 额度**：额度不足时仅推迟候选。优先释放闲置 active 页，
   已在执行或 DMA 在途的页不回收。CPU 历史额度与 GPU active 额度分别结算。
5. **分配剩余计算与搬运资源**：普通增量 prefill 使用原生剩余 token 预算；
   恢复由有界后台生产者推进。没有可运行模型请求时尽快完成补位；已有模型
   工作时，根据测得的资源竞争决定搬运份额。

调度器输出的是本步的请求集合、补位对象、prefill 额度和搬运许可。KVMem
负责合法选页、检查点、持久历史和完成事件；vLLM 负责实际 batch 与原生页。
这些部分通过同一份就绪状态和额度交接，不能各自重复准入或重复计费。

## 请求状态

| 状态 | 可以做的工作 | GPU 页处理 |
| --- | --- | --- |
| 等待工具 | CPU 历史与检查点发布；工具在独立执行资源中运行 | 已发布且精确的 M active view 可暂留，随时受压力回收 |
| 等待准入 | 等待 CPU 历史增长额度及 GPU 生命周期额度 | 不新增模型页 |
| 恢复中 | 后台准备所选 active KV、恢复模型状态、检查 fence | 只保留本请求的独占租约，不能提前加入公共 batch |
| 增量 prefill | 处理已验证历史之后的新 token；必要时执行既定 Query 重放 | 在已准入页内增长 |
| decode | 参加原生连续 batch | 保留 active 及已承诺的本轮生成额度 |
| 退休中 | 发布最终已接受历史和终态检查点 | 完成确认后才允许转交、缓存或释放 |

工具返回需要先验证会话 generation、前缀 token 和检查点。JSON 参数等价
只能用于识别相同的已接受消息，不能改变原始 token 或掩盖真实历史修改。
精确 M 命中时恢复原 active view；确需 P 回退或重新选页时沿用原语义。

## active 驻留规则

驻留的作用是省掉下一轮 active KV 的重建和上传。它是可撤销的闲置缓存，
不是工具等待期间继续占用一个不可回收的 active 配额。

- 只接纳正常结束、完整 CPU 历史已发布、精确 M 检查点已确认的 attention 页。
- 同会话、同 generation、同历史位置及同 active view 才能直接转交原生页。
  recurrent / MTP 模型状态仍按其检查点契约恢复。
- 分配新工作和保证活跃请求未来增长时，先回收闲置页，再决定是否等待。
  在途恢复和执行中的页受 fence 保护。
- 采用有界 LRU 撤销。离线 P1 不按时间失效；仅在容量压力、明确会话清理或
  检查点身份变化时回收，不用猜测工具何时完成。
  只有证明 LRU 导致可量化的重复搬运后，才引入更复杂的收益预测。

缓存容量上限是空间边界；可选有限 TTL 属于另一种失效策略，不能直接当成吞吐最优参数。
必须记录命中、省下的上传字节、压力撤销，以及是否延迟了新工作准入。

## 补位排序和成本依据

候选的成本是从当前状态到可运行 decode 的剩余关键路径时间。区分以下部分：

- CPU 准备：选页、CPU gather 与模型状态准备的测量耗时。
- 搬运：实际需要上传的字节和同等竞争条件下测得的有效带宽。
- 输入计算：剩余新增 token 的 prefill 成本，以及必须原子执行的 Query 重放。

CPU 准备与 GPU 工作有重叠时按依赖关系估计关键路径，不简单把所有时间相加。
成本使用历史观测的保守估计；缺少样本时沿用队列顺序，不凭空给出精确分数。
以较小剩余成本优先补位，并用等待年龄兜底，避免一个新来的短请求序列
永久压住已经等待的长请求。此启发式需要验收，不声称全局最优。

原始 16 个任务组成待处理队列。工具等待者是否允许入口启动更多 agent，
取决于 CPU 历史准入和入口在途限制；GPU 实际计算始终不超过 4 路。
若只允许 4 个 agent 在途且四者均等待工具，GPU 暂时空闲是供给不足。
提高入口在途数量需要在基线和候选两边保持一致，另列对照，不能混入收益。

## prefill 与搬运规则

普通 prefill 从**已经验证的历史末端**开始，处理新增内容。原子 Query 重放
维持既有边界；共享 chunk 额度不能把它拆开。其成本要单独记录，不能承诺
开启 chunked prefill 后所有干扰都会消失。

初版沿用已有离线配置的 2048-token 普通分块和原生总预算。当前样本曾观察到
更小分块降低整批效率，因此不先固定缩到 512。后续要改变分块，先比较相同
decode 数、上下文长度和 MTP 推进量下的新增 prefill 成本，扣除固定维护成本。
只有能解释“更快补位”与“拖慢现有 decode”的总收益时，才改变全 batch 额度。

恢复保持有界单生产者和独占 staging，避免多个恢复重复争抢 CPU gather / DMA。
GPU 没有可运行请求时全速推进。GPU 有工作时，先测实际 H2D 竞争与 stall，
再决定是否限制上传提交；固定 8 GiB/s 只可作为诊断，不能直接作为生产策略。
CPU 线程、GPU 计算和 PCIe 带宽分别记录，不能把 host 调度预算称为 GPU 时限。

## 证据与验收顺序

已有 r16 窗口中，纯 decode 模型步中位数为 41.0 ms，混合 prefill 为 436.6 ms；
两类并发组成不同，这些数值只用于定位。121 次恢复的中位耗时为 2.04 秒，
其中 host 准备中位耗时为 1.71 秒。它提示优先消除重复恢复和准备成本，
不能据此断言带宽限速一定有效。原始记录：
`artifacts/deepswe-first16-20261015-r16/decode-variance-20261015.json`。

1. **生命周期正确性**：真实模型验证跨轮热命中、CPU 冷恢复、压力撤销、TTL
   失效及取消；逐请求核对 target / MTP KV 和 recurrent 状态，验证用户隔离。
   有限 TTL 回归组 `Pttl` 检查 TTL 冷恢复、冷恢复在途取消、热恢复后 decode
   取消及原检查点再续接。生产候选 P1 另外验证热取消、跨越旧 TTL 的热返回。
   取消后的再续接也必须通过完整 KV / recurrent 逐字节验证，不能只核对长度。
   独立隔离检查使用四个不同的用户历史，每轮完整输入指纹必须互异。
   独立 `Ppressure` 故障注入使用 32K 初始上下文、四路退休屏障和 7.5% 闲置页上限，
   强制部分 active view 撤销；采用与 P1 相同的压力驻留，不参与性能比较。
   验收同时要求确有压力撤销、热/冷逐字节恢复，以及请求清空后的
   `free_pages + idle_pages = total_pages - null_page` 和 CPU 额度守恒。
   这些场景失败时停止后续性能与正式任务；不能把降低缓存容量当作调优结果。
2. **只比较基线与统一策略**：固定输入与工具等待、输出长度、模型参数及请求
   供给；先测一套策略，不做无假设的参数排列。每次决策记录候选状态、所用
   额度、成本依据和等待原因，能从轨迹解释一次长停顿。
3. **单项消融**：观察到明确损失后，仅关闭对应机制验证因果；例如关闭驻留
   应恢复相应上传量，限制搬运必须证明提高了有效吞吐。固定 512 / 8 GiB/s
   的组仅保留为显式诊断，不作为默认主验收矩阵。
4. **原始 first16**：A0、P1 使用同一份冻结源码与修复后的桥接器，分别运行
   相同样本、工具与隐藏评分协议，K128K + G128K、4 并发、
   CPU 历史不落盘。正确性通过后运行完整任务，报告整批耗时、有效输出吞吐、
   恢复延迟和 decode 间隔，同时列出 prefill / 恢复占用与工具空窗。

性能目标是多轮有效吞吐相对基线提升至少 10%，纯 decode 无可重复退化。
若未达到，保留未通过结论并按决策轨迹定位；不能以 CPU 测试通过、GPU
利用率升高或某一片段更快替代完整验收。

## 只读归因分析

`scripts/analyze_agent_scheduling.py` 对原始日志作后处理，不改变冻结的服务
代码或负载。`--traces <case/traces.json>` 用精确请求 ID 排除预热与清理；
实时基线可用 `--last-seconds 900`。统一输出：

- 已接受输出的整段吞吐与事件间隔。MTP 一次事件可能包含多个 token，不能
  将事件间隔直接称为每 token 延迟。
- 纯 decode、纯 prefill、混合步的模型与维护耗时；按并发组成和实际 active
  长度分组。旧版本缺少长度时明确标为未知，不能声称已经控制所有变量。
- 恢复提交前的等待/准备与提交后的服务时间。host gather 是服务时间的组成
  部分，不能重复相加，也不能把上传字节除以服务时间当作 PCIe DMA 带宽。
- 恢复在途与 decode 步耗时的相关性；这里只用 host 时间戳，不能替代 GPU
  kernel 级 profiling 或对照实验的因果证据。
- 成本模型覆盖：可补位候选中有估计的数量、竞争候选全部具备估计的快照数，
  以及后台恢复估计覆盖。排除 decode 的零剩余成本、预热和其他请求。
  计数来自状态变化快照，不是时间占比；具备估计也不代表一定改变了排序，
  老化与资源额度仍可决定最终顺序。

该分析器单独通过 11 项 CPU 检查；不改变主验收门槛，也不将正确性 oracle
开启时的额外成本混入性能收益。原始采样覆盖的 prefill 速率仅用于解释，
不外推为整个测试的 prefill 吞吐。

正式 DeepSWE 桥接器向模型发非流式请求，不能从桥接响应构造逐输出事件时间线。
`scripts/observe_formal_latency.py` 因此单独只读采集原生
`vllm:inter_token_latency_seconds` 直方图及输出/抢占计数，每两秒一次。
它在 Query、短尾、完整 G 和清理四项预检全部通过后才采集，只读取当前正式组，
避免 A0/P1 复用同一端口时把下一组的计数归到上一组。两组使用同一采集器；
其代码指纹、进程及启动时间在 `r6/latency-observer-process.json`，数据保存于
各组的 `latency-metrics.jsonl`。采集器不修改冻结的推理和工作负载代码，另通过
7 项检查，覆盖预检计数扣除、直方图区间、计数重置及组间隔离。

这里按已安装 vLLM 的实现解释：该直方图记录相邻 `EngineCoreOutput` 的时间差，
MTP 可在一次输出中携带多个 token，因此称为原生输出事件间隔。p95 使用累计
直方图差值给出所在桶的上下界，不把分桶近似称为精确分位数。完整任务口径
还必须核对首个快照结束早于首个正式请求、末个有效快照覆盖最后一个正式
响应，并排除计数重置；尚未通过这些边界检查时，只能报告有明确起止的局部
窗口。TTFT 和每请求平均输出时间另外使用桥接器保存的逐请求指标。
`scripts/analyze_formal_latency.py` 实施这些边界检查，并核对开始/结束事件成对、
16 个任务均结束及采集器版本一致；未闭合请求不能仅凭任务状态就视作已覆盖。
该后处理另通过 8 项检查，和采集器共 15 项。正式结果写为各组的
`formal-latency.json`；没有正式请求时明确输出未完成，不回填预检分位数。

## 桥接层长历史准备修复

2026-10-16 对仍在运行的 r16 检查发现，部分请求已经进入 Claude 消息流，
但尚未提交 vLLM。旧回退路径为每个历史消息的四个边界分别重新编码整个前缀。
koota 第 189–196 轮的准备记录为每轮约 225–242 秒，不能算成工具等待或 GPU prefill。

`PrefixTokens` 先对原始输入编码一次，再以完整、非 stripping、非 normalized 的
Qwen 消息分隔 token 为边界，局部重编码到所需位置。Qwen 的 NFC 在这些
分隔符之间生效；其他未验证的 normalizer 保留精确回退。不能直接对普通
BPE token 的 offset 做二分计数，因为截断词片段可能得到不同的 token 序列。
已接受的旧输出 ID、协议渲染、Query 和 mandatory 坐标语义均不改变。

`scripts/audit_deepswe_coordinates.py` 以保存的原请求进行 CPU 回放：

## 根据首对测量修正驻留规则

`r5` 第一对结果：多轮 agent 整段有效输出吞吐 A0 为 74.97 token/s，P1 为

这只有一对，不满足三对验收，也未达到 10% 的目标。不能用热命中率替代收益。

16 次跨轮返回中 P1 有 12 次热命中、4 次冷恢复。冷恢复均与 5 秒 TTL 失效对应，
而工具等待包含 6 秒；记录到失效的决策快照仍有 317–435 个空闲原生页，
没有容量压力撤销。四次冷恢复累计上传 31.16 GB，服务耗时中位数 6.68 秒，
排队和服务合计中位数 7.24 秒。host 准备属于服务时间，不能重复相加。

因此只修改这一条规则：P1 设置 `active_resident_pressure_only=true`、TTL 为零，
有空间时保持精确 M active 页，达到闲置页容量上限或新工作需要额度时按 LRU
回收。0.5 闲置池上限、活跃请求未来增长预留、fence 和所有身份校验不变。
这不意味着无限持有显存：任何新准入都可以优先撤销闲置页。
有限 TTL 仍作为独立可选模式和正确性回归 `Pttl`，不能与压力驻留同时开启。

预期因果链为“消除无容量收益的回收 → 减少恢复上传和排队 → 更快加入 decode”。
保持原工作量，不缩短工具等待来提高命中率，不同时调整 prefill 分块或搬运速率。
新的隔离验收必须实际观察到超过旧 TTL 的热返回、完整 KV 字节相等、没有过期；
压力验收仍须观察到真实回收、随后 CPU 冷恢复和资源守恒。
之后重新完成三对 A0/P1 测量；旧版首对仅保留为诊断，不拼入新版中位数。

冻结后的正常性能比较完整跑完三对再决定是否接受。只有正确性错误、外部 GPU
争用或明确的实验配置错误才提前中止；不因某个短窗口快慢切换参数。
