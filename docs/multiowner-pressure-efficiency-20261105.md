# 六路 prefill 重选等待与效率验证

本轮按用户要求先抓稳定阶段轨迹、根据证据优化，再用无 profiler 的完整输入验证吞吐；
通过后运行原 MAB。此前持久目标已清除，本轮没有重新建立目标或定时巡检。

控制：原六个 MAB 冷前缀，共 2,366,464 历史 tokens；NVFP4、Active=36864、Gen=16384、
block32、sink41、recent0、原采样和输出上限不变。逐层累计 attention pressure、逐层 Mean-K
Query 不变。CPU 缓存为用户已授权的 112GB；原生 batch 上限 16424。逻辑提交仍为 1K。
纯 prefill 测量保留原有限队列门控，排除加载、Query 和 decode；不等于连续 MAB 服务吞吐。

## 稳定阶段轨迹发现

两边均使用完整原始输入，首次观察请求到达 96K 后抓取约 8 秒；工具停止与落盘会额外耗时。
两组运行都只作诊断，不能使用其吞吐。

- 候选轨迹有效 GPU 窗口 8.192s，GPU 工作并集 7.553s，空闲 0.639s（约 7.8%）。
  主线程确认的 GIL 等待 1.068s，其中与 GPU 空闲重叠 0.250s。这不证明 GIL 是唯一主因。
- `assembly_queued→assembly_started` 并非全是排队：`assembly_started` 在逐层准备后发出。
  新分析按 command 的 worker marker 关联，避免把前一个请求的准备算进后一个请求。
- 候选 command19 在通道已经释放后，仍从 queued 到 worker 空等 1.079s；提交动作推迟到
  下一次前台模型迭代。旧轨迹类似事件等 0.640～0.741s。更大的前台计算批次放大了这个空档。
- 候选捕获的四次组装共创建 72 个 assembler（父组装器+17层子组装器），`from_runner`
  累计 0.942s，约235ms/事件；旧轨迹两次共36个，累计0.286s，约143ms/事件。
  候选组装线程的 `cudaStreamSynchronize` 累计0.711s；逐层页表克隆/`.item()` 检查是可删除的
  重复同步来源。此项与其他 GPU 工作重叠，不能直接当作可回收的全局墙钟。
- 组装完成仍需主线程看到 CUDA fence 并提交，之后才释放唯一组装通道；较长的前台迭代也
  拉长完成交接和后续请求的等待。已经启用 post-forward 完成检查，不能误报为未复用。
- 当前冻结代码已经包含 physical-slot/order 元数据缓存、prepared CPU reader，不重复计为新改进。
  归档读取和发布仍有 CPU 工作/竞争；本轮不根据“wall minus thread CPU”直接推断 GIL 持有者。

证据：`artifacts/multiowner-6000-publication-profile-20261105-r1` 与
`artifacts/multiowner-6000-baseline-profile-20261105-r1`。各自保留 Nsight、SQLite、NVTX、
线程 CPU 时钟与首份完整模型回答。捕获窗口没有逐项解释首轮5.80s的所有波动。

逐事件复核`historical-wait-distribution.json`：首轮132次等待的中位数5.987s、p90 9.008s，
四个按时间排列的33事件分组均值为6.329/6.134/5.830/4.910s；第二轮为3.454/3.463/3.132/2.625s。
因此不能归因于少数启动/JIT离群点。旧1.71s拆为排队及准备0.833s、组装0.551s、完成交接0.258s；
首轮5.80s对应3.196/1.447/1.072s，第二轮3.17s对应1.589/0.876/0.560s。
原版567次模型调用，多owner首轮325次，前台单次循环变长，放大离散轮询及单通道排队；
首轮为何比同版后续多约2.63s仍没有同时段主机轨迹作完整归因，不虚构NUMA或GIL占比。

## 第一组改动及实测

优先复用已有实现，增量移植到冻结 v2，不覆盖原 RoPE 或其他召回代码：

1. 准备完成时立即尝试提交后台组装，沿用原 lane/transfer credit/fence。通道忙时仍排队。
2. 同一暂停事务内，子组装器借用父组装器已验证的私有页表，不再逐层克隆和同步检查；
   请求、页表身份/版本、生命周期和全部 DMA/consumer fence 仍验证。

工作区新增显式默认关闭的 `--layerwise-pressure-submit-on-prepare` 开关；未改变 serving 默认值。
正式候选在单独冻结版本显式启用。prefill CPU 检查91项通过；实际GPU字节12项通过，覆盖
层0/8/16、native页64/1616、完整块/部分尾块、prepared reader与borrowed view组合。
初始CPU测试误含工作区后续decode扩展，原冻结版本本来就拒绝该路径；失败证据保留，
随后的检查限定原prefill范围。并未为通过测试修改decode行为。

`artifacts/multiowner-pressure-fix-bench-20261105-r2` 预声明顺序为：
只提前提交、组合第一次、组合第二次、未修改对照。所有数据从原输入独立执行；不因输出差异重采样。
旧A/A本身也改变批次形状和块轨迹，完整输入的固定形状验证另用最长冷前缀及其后续问题进行。
测试工具准备阶段修正过报告函数名称，未运行的r1保留，实际使用r2。

## 无 profiler 完整输入结果

每轮独立运行同六份原始完整输入，132次prefill压力重选，统计排除Query/decode。

| 策略 | 纯prefill tokens/s | 挂起→ready | 排队及准备 | 组装开始→提交 | 提交→ready |
|---|---:|---:|---:|---:|---:|
| 仅准备后立即提交 | 5414.58 | 1.602s | 0.235s | 0.773s | 0.500s |
| 再复用逐层页表，第一次 | 5421.42 | 1.577s | 0.238s | 0.706s | 0.544s |
| 相同组合，第二次 | 5415.02 | 1.642s | 0.221s | 0.740s | 0.595s |
| 随后原版对照 | 5526.07 | 3.169s | 1.604s | 0.861s | 0.561s |

因此确认压力等待减少约49%，但不能认定纯prefill提速；组合均值5418.22比随后原版
低约1.95%，也处于此前v2的5204–5489波动附近。模型CUDA事件区间各约406–407s，
不是纯kernel时间，不能把它和压力累计owner秒直接相减归因。原版对照更多批次只含4个
请求，优化组更多5/6个请求；动态批次组成随维护时机改变，吞吐与单请求暂停时长不线性对应。

## 进一步候选：利用现有统计容量的余数

原bank为448行，每1K逻辑块需32行，可容纳14块；平均向下取整给六路各2块只用12块，
八路各1块只用8块。新增默认关闭的`prefill_physical_fill_rows`，保持基本配额，轮流分配
剩余完整逻辑块。六路可为3/3/2/2/2/2、八路2/2/2/2/2/2/1/1。block、预算、逻辑1K提交、
统计容量、最大每请求8块均不变；混合Query/decode仍使用原路径。此处改变物理批次形状，
使用用户已授权的有限精度差异范围，不宣称动态多请求输出逐位一致。

CPU94项、GPU8项通过，GPU覆盖六路不等长及八路混合完整448行统计隔离、原FA2输出、
FP32分数oracle和17层共享DMA字节。实验`artifacts/multiowner-row-fill-20261105-r1`
按预声明b1、b2、原组合control顺序执行，无profiler。b1为5411.40、b2为5424.93 tokens/s，
随后control为5420.71 tokens/s，候选均值5418.17，与对照几乎相同。b1调用数261（原组合304）、平均9063 tokens/步，
模型事件403.84s（原组合406.05s），组装提交→ready却从0.544s增至0.954s。
调用数下降不能等同于总体提速；该候选没有纳入MAB。

## 下一项：复用原生统计静态快捷路径

实测GPU窗口主要时间仍在前向attention，转向已有`action_native_prefill_static_aligned`。
当前六路运行明确关闭它。20261104组件的16个GPU失败为构建环境问题；本轮使用包含venv/ninja
的完整工具PATH，并在当前冻结runtime上重新核验（native_attention及build源与该旧组件相同）。
新增六路/八路GPU fixture显式核验static真实dispatch，避免开启选项却一直走generic。
`artifacts/multiowner-static-native-20261105-r3`仅改变该已有配置开关，不叠加row-fill。
29个host及42个GPU检查（共71项）已通过，随后按b1/b2/control测相同完整六输入。
本轮完整输入已完成：b1=5655.73、b2=5641.96、随后control=5441.03 tokens/s。
两轮候选合并5648.83，比该匹配control高3.819%；前向事件区间389.95/389.22s，对照405.55s。
两轮均超过本轮未修改多owner control的5526.07，合并净提升2.222%。目标6000尚未达到。
重选等待1.514/1.530s；原版未改control为3.169s。静态实际dispatch分别见各自native报告，
并已核验来源指纹、容量相同、无producer验证失败。row-fill仍未采用。
`efficiency-validation.json`只批准性能门槛；MAB固定输入一致性仍单独验收，未把动态批次
相同最终答案当作全轨迹字节一致，也不声称该小规模对照具有统计显著性。
r1遗漏测试依赖，在采集前失败；r2数值检查通过，但source-header测试定位错误，新增多owner
夹具本来包含非对齐分段却错误要求static dispatch。r3修正测试定位，并同时保留未对齐保护
和新增对齐快捷路径检查；没有修改生产内核或删除失败断言，旧证据均保留。
